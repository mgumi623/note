# AI時代のエンジニアスキルと働き方の将来

## はじめに：あなたの認識は正確です

あなたが感じている問題意識は、2025-2026年のエンジニアリング業界の実態を正確に捉えています：

1. **「AIの進出でコーディングが置き換わってきている」** ← 実際に起きている
2. **「エンジニアに求められるのは包括的なスキルセット」** ← その通り
3. **「企業内での自社アプリ内製化・運用が主流に？」** ← 既に進行中

本ノートは、これらについて詳細な根拠と、医療業界（病院）での具体的な実例を含めて、整理します。

---

## 第1部：AIによるコーディングの自動化と、それが意味すること

### 1.1 現状：コーディングはもう「ルーチン化」している

#### 何が起きているのか

2025年時点で：
- **開発者の84%がAIツールを使用**している
- GitHub Copilot、Amazon Q、ChatGPTなど複数のツール選択肢が存在
- 「コーディング」という作業のかなりの部分がAIで自動化可能に

#### 具体的なシナリオ

**従来（2020年）**:
1. 要件定義 → 手作業でコード設計 → 手書きコード → テスト → デバッグ → リリース
2. スケジュール：機能1個に2-3週間

**現在（2025年）**:
1. 要件定義 → AIにプロンプト入力 → AIが自動生成 → テスト → AI出力の検証 → リリース
2. スケジュール：機能1個に2-3日（10倍高速化）

**ただし新しい課題**:
- AI生成コードは「信頼度29%」（2025年後半）
- 理由：AI生成にはロジックエラーが含まれることが報告されている
- 「多くが使うが、信頼できない」という「信頼のパラドックス」が発生

### 1.2 では、エンジニアは何をするのか？

#### 「コーディング」という作業が価値を失う

昔のエンジニアの価値：
```
「複雑な要件をコードに翻訳できる」
 ↓
 これがエンジニアの核となる価値だった
```

現在：
```
「複雑な要件をコードに翻訳できる」
 ↓
 AIがやってくれる（ただし完璧ではない）
```

#### では、誰が価値を持つのか？

**AI時代に価値が高まる3つの領域**:

1. **設計・アーキテクチャ力**
   - 「何をAIに任せるか」「何は人間の判断が必要か」を決める
   - システム全体を俯瞰する思考
   - 複数層の相互作用を理解する

2. **検証・品質保証力**
   - AI出力の正当性を検証する
   - セキュリティ・パフォーマンス・エッジケースを確認
   - 本番環境での予測不可能な動作に対応

3. **戦略・ビジネス思考**
   - なぜこのシステムが必要なのか理解する
   - ビジネス要件をシステム要件に翻訳する
   - ROI・コスト最適化を考慮した設計

### 1.3 労働市場の大きな転換：「ジュニア層への打撃」

#### 最も影響を受けるのは若手エンジニア

**実態**:
- ジュニア層が担ってきた「ルーチンコーディング」がAIに代替
- 若手（22-25歳）の雇用が最大20%減少する可能性
- 従来の「ジュニア → シニア」への成長パスが不明確に

**なぜジュニア層か？**:
```
従来のジュニアの役割：
「成文化された知識に基づくルーチンワーク」
 ↓
これが最もAIで自動化しやすい
```

**一方、シニア層は？**:
```
従来のシニアの役割：
「複雑な問題の判断」「意思決定」「設計」
 ↓
AI時代には、これらがさらに重要に＋新しいタスク（AIの監視）も増加
```

#### 「キャリア二分化」のリスク

```
高度なスキルを持つエンジニア
 ↓
 AIを武器として使いこなす
 ↓
 生産性が3倍以上に向上
 ↓
 市場価値が上昇し続ける

vs.

基礎スキルのみのエンジニア
 ↓
 AIに仕事を取られる
 ↓
 相対的に価値が低下
 ↓
 市場価値が停滞・下降
```

### 1.4 新しいエリート職種：FDE（Forward-Deployed Engineer）

#### 何か

**FDE = AIモデルを実装・カスタマイズする専門家**

- AIモデル自体を作る（MLエンジニア）ではなく
- AIモデルを組織に適した形で統合・運用する人材

#### 仕事内容

- AIの出力を組織のプロセスに統合
- AIの精度を組織に合わせてチューニング
- AIが出す結果を監視・改善

#### 市場価値

- AIブーム初期なので、市場価値が急速に上昇
- 米国シリコンバレーで既に「FDE」の採用が活発化
- 日本でも今後需要が高まる職種

## 第2部：なぜ「フルスタック化」が避けられないのか

### 2.1 あなたの指摘「フロントだけじゃない、データベースだけじゃない」

#### 従来の専門化モデル（2000-2015年）

```
フロントエンドエンジニア
  ↑
  ↓
  各層が独立して専門化
  ↓
↑ ↑ ↑
│ │ │
バック  DB  インフラ
エンド
```

**メリット**:
- 各人が極度に専門化
- 深い知識が蓄積

**デメリット**:
- 層間の調整が必要
- コミュニケーション時間が長い
- ボトルネック多発

#### なぜ今フルスタック化が必要か？

**理由1：DX推進には「スピード」が不可欠**
- ビジネス環境の変化に素早く対応する必要
- 層間の調整で時間を費やす余裕がない

**理由2：アジャイル開発への適応**
- スプリント（2-4週間）で機能を完成させる必要
- 複数の専門家の調整では間に合わない

**理由3：クラウド時代の構造変化**
- サーバーがクラウド化されて、物理的な「バックエンド」という概念が薄れた
- フロント・ロジック・ストレージが密接に統合
- 各層が密接に関連しているため、層の専門化が逆効果に

**理由4：内製化の推進**
- 外注で「専門家を多数配置」という戦略が使えない
- 限られた人数で全層をカバーする必要

### 2.2 「フルスタック」の正確な定義と誤解

#### よくある誤解

「フルスタック = 全部できる天才」

これは間違い。実際には以下の意味：

#### 正確な定義：「T字型スキル」

```
    ↑（深さ）
    │
深い │       ●深い専門性
     │     / \
     │   /     \
広い │─────────────  幅広い基礎知識
     │
     └─────────────→
```

**実際のイメージ**:
- **横軸（幅）**：フロント・バック・DB・インフラ・セキュリティなど、全層の基礎を理解
- **縦軸（深さ）**：その中で「自分はこれが専門」という領域を1-2つ持つ

**例**:
- 「自分はバックエンドが専門だけど、フロント・DB・インフラの基礎は理解している」
- 「データベース設計が得意だけど、アプリロジック全体も理解できる」

#### なぜこれが強いのか

```
従来型（I字型）：
「データベース専門」→ DB設計は完璧 → しかしフロントが変わるとわからない → 影響分析ができない

T字型：
「データベース専門」→ DB設計は完璧 → かつフロント・ロジックも理解 → 全体最適化を提案できる
```

### 2.3 具体的な適用例：医療現場

#### 例1：患者管理システム

**I字型（層別専門化）の場合**:
```
要件：「患者の受付から診療までの流れを自動化したい」
  ↓
フロント：受付画面を作成
バック：患者データベースのAPI作成
DB：テーブル設計
  ↓
問題発生：
「フロント画面から送られてくるデータの形式と、
 DBに保存される形式がズレている」
  ↓
仲介者が調整 → 時間がかかる
```

**T字型（包括的理解）の場合**:
```
要件：「患者の受付から診療までの流れを自動化したい」
  ↓
一人のエンジニア（T字型）が全層を理解しながら設計
  ↓
「受付画面はこう、データ形式はこう、DB構造はこう、
 これらが整合するように設計する」
  ↓
修正・調整が最小限に
```

#### 例2：医療データ分析アプリ

**必要なスキル領域**:
1. **フロント**：グラフ・チャートの表示方法
2. **バック**：分析ロジック・集計SQL
3. **データベース**：大規模データの効率的なクエリ設計
4. **インフラ**：クラウドコストの最適化

**I字型の場合**：各専門家が1人ずつ必要（4人）
**T字型の場合**：1-2人で対応可能（コスト1/2以下）

### 2.4 「フルスタック化」へのロードマップ

#### 段階1：自分の得意領域を極める（現在）

- バックエンドが得意なら、バックエンドの深い知識を習得
- これは変わらない

#### 段階2：隣接領域を学習（1-2年）

- バックエンド専門なら、フロント・DB・インフラの基礎を学習
- 「完全な専門家にはならない、でも理解はできる」レベルを目指す

#### 段階3：全体設計への参加（2-3年）

- システム全体の要件から設計をリード
- 複数層を同時に最適化する提案ができる

## 第3部：内製化の時代へ：あなたの医療機関での働き方は変わるか

### 3.1 「内製化」が進むのは本当か？

#### 結論：YES。既に進行中。医療機関も例外ではない。

**背景**:
- 2025年の崖：レガシーシステム刷新の急務
- DX推進：ビジネス変革にはスピードが必要
- テクノロジー進化：ノーコード・AI開発支援により、内製が容易に
- コスト圧力：外注より内製が長期的に安い

### 3.2 医療機関における内製化の特殊性

#### 医療機関が内製化しやすい理由

1. **独自の業務プロセス**
   - 各病院・医療機関により異なる
   - 「既製品」では対応しきれない
   - 必然的に「カスタマイズが必要」 → 内製化のきっかけに

2. **高いセキュリティ・プライバシー要求**
   - 患者データは最高レベルの保護が必要
   - 「外部のベンダーに預けるのは不安」という心理
   - 内部で管理する方が安心感がある

3. **診療現場との距離**
   - 医療スタッフの細かい要件を深く理解できる
   - 外注では「医療現場の動き」を理解しない設計になることも
   - 内製なら「医療スタッフと直接相談しながら開発」可能

#### 医療機関が内製化しにくい理由

1. **IT人材の不足**
   - 地方の中小病院では特に深刻
   - 「プログラマーがいない」という状況

2. **給与・待遇**
   - IT業界より医療業界の給与は低いため、人材獲得が困難

3. **現在の業務負荷**
   - 既存システムの保守運用で人手がいっぱい

### 3.3 医療機関での内製化の実例

#### 実例1：済生会熊本病院

**背景**:
- 購買案件管理システムが老朽化
- ベンダーのシステムでは医療現場のニーズに対応していない

**施策**:
- **Microsoft Power Apps** というローコード開発ツールを導入
- 医療情報システム室が中心
- **他部署のスタッフも「市民開発」に参加**

**成果**:
- 老朽化したシステムを自社で刷新
- 医療スタッフが「システムをカスタマイズできる」という体験を獲得
- 組織全体でDX意識が向上

**重要ポイント**:
- ローコードツール活用により、プログラミング知識がなくても開発可能
- 「医療スタッフも開発者になれる」という発見

#### 実例2：さきがけホスピタル（地方病院）

**背景**:
- 独自の医療プロセスを持つ地方病院
- 既製品では対応不可

**施策**:
- 院長がトップダウンでDXを推進
- **Claris FileMaker** を使用して独自システムを開発
- 職員への開発トレーニング実施

**成果**:
- 「Sakigakeシステム」という独自の業務システムを完成
- システムのメンテナンスを職員が担当可能
- 院全体の「デジタル文化」が成熟

**重要ポイント**:
- リーダーシップ（院長の強い意志）が成功の鍵
- 継続的な人材育成投資が必要

#### 実例3：春日井市民病院（AI活用による超高速内製化）

**背景**:
- IT知識がない地方病院
- 内製化に対する不安「プログラマーがいないのに、できるのか？」

**施策**:
- **Amazon Q Developer**（AWSのAI開発支援ツール）を活用
- AWS内製化支援プログラム「ANGEL Dojo」に参加
- **「共創型内製化」**を実施

**成果**:
- **わずか4日で以下を実装**：
  - 病床管理システム
  - 医療文書作成支援アプリ
- IT知識がなくても、AI支援があれば開発可能を実証

**重要ポイント**:
- AI開発支援により、人材不足を補完可能
- 「できた！」という成功体験が次の施策につながる

### 3.4 医療機関での内製化の課題と解決策

#### 課題1：IT人材の不足

**課題の詳細**:
- 地方病院では特に深刻
- 既存システム保守で手一杯
- 新しいシステムを開発する余裕がない

**解決策**:
- ローコード・ノーコードツール活用（人材育成まで含む）
- AI開発支援ツール（プロンプト入力で高速開発）
- 外部パートナーとの「共創型」での段階的内製化

#### 課題2：セキュリティ・品質保証

**課題の詳細**:
- 患者データの安全性が最優先
- 内製化によって「品質が低下する」リスク
- 医療法などの規制対応が複雑

**解決策**:
- ガバナンス・監査体制の整備
- セキュリティチェックリストの作成・運用
- 定期的な外部セキュリティ監査
- AI生成コードの検証プロセス構築

#### 課題3：組織文化

**課題の詳細**:
- 「昔のやり方」に慣れている
- 新しいシステム導入への抵抗
- 医療スタッフの多忙さ

**解決策**:
- トップ（院長など）のリーダーシップ
- 段階的な導入（1つの部門から開始）
- 成功事例の共有
- 医療スタッフの「声」を最大限反映

### 3.5 あなたの病院での働き方はどう変わるか？

#### パターン1：従来モデルの継続（可能性：低）

```
現在：
病院の内製チームが外注会社に開発を依頼
  ↓
外注会社がシステム構築
  ↓
納品・保守

この構図は続く（一部は）
```

#### パターン2：ハイブリッド型（可能性：中）

```
新しい働き方：
病院の内製チーム（あなた含む）が主導
  ↓
「医療スタッフも開発に参加」（市民開発）
  ↓
「複雑な部分だけ外注」（外注会社との協業）
  ↓
継続的にシステムを改善・発展

医療スタッフ → あなたたちエンジニア → ビジネスロジック作成
あなたたちエンジニア → 外注会社 → 複雑なシステム実装（例：AI統合）
```

#### パターン3：完全内製化（可能性：中-高）

```
将来の働き方：
病院が自社で大部分のアプリ開発・運用を実施
  ↓
あなたの役割が拡大：
  - アプリ開発（従来通り）
  - +アーキテクチャ設計（全体最適化）
  - +ノーコードツール導入・管理
  - +医療スタッフへのトレーニング
  - +セキュリティ・ガバナンス
  ↓
あなた＋医療スタッフの「市民開発者」で大部分をカバー
外注は「最新テクノロジー活用」など高度な領域のみ
```

## 第4部：あなたが今からすべき準備

### 4.1 スキルセット：現在から5年後への進化

#### 現在のスキル（2026年）

仮定：バックエンド開発が主流
- 言語（Python、Node.js など）
- フレームワーク（Django、Express など）
- データベース設計（SQL、NoSQL）

#### 1年後に追加すべきスキル

**AI開発ツールの習熟**:
- GitHub Copilot / ChatGPT の実践活用
- プロンプトエンジニアリング
- AI生成コードのレビュー・検証方法

**フロントエンド基礎**:
- HTML / CSS / JavaScript の基礎
- React や Vue などの主流フレームワーク
- 「フロント側がどう動くか」の理解

**セキュリティ意識**:
- 患者データの扱い（医療法等）
- 暗号化・認証・認可の理解
- セキュアコーディング

#### 3年後に持つべきスキル（T字型の完成）

**アーキテクチャ設計**:
- マイクロサービス / モノリシック の選択
- スケーラビリティ・パフォーマンスの考慮
- セキュリティ・運用性を考慮した設計

**ビジネス理解**:
- 医療スタッフの業務フローを深く理解
- 医療経営・採算性の基礎知識
- 「なぜこのシステムが必要なのか」をビジネスから説明できる

**内製化推進能力**:
- ローコード・ノーコードツール（Power Apps、Figma など）の活用
- 医療スタッフへのトレーニング方法
- チーム管理・リーダーシップ

### 4.2 キャリアパス：3つの選択肢

#### 選択肢1：「プロダクト型」エンジニア

```
役割：
 自社（病院）のアプリをオーナーシップを持って開発・運用

メリット：
 - 医療スタッフの顔が見える（やりがい）
 - 自分の仕事がビジネスに直結（わかりやすい）
 - キャリアが安定している可能性

デメリット：
 - 給与が相対的に低い（医療業界）
 - 最新テクノロジーから遠ざかる可能性
 - 組織依存度が高い

向いている人：
 - 「ビジネスとの一体感」を大事にしたい
 - 安定を重視
 - 医療に興味がある
```

#### 選択肢2：「コンサルタント型」エンジニア

```
役割：
 医療機関のDX推進・内製化をサポートする外部人材に転職

メリット：
 - 複数の医療機関を見られる（広い視野）
 - 給与が相対的に高い（IT業界）
 - 最新テクノロジーを常に追いかける

デメリット：
 - 長期的な関係構築ができない
 - 責任が限定的
 - キャリアが不安定（契約ベース）

向いている人：
 - 「複数プロジェクトの経験」を重視
 - 給与重視
 - 最新テクノロジーに常に触れたい
```

#### 選択肢3：「リーダー型」エンジニア

```
役割：
```

## 第5部：医療機関での内製化への実装ロードマップ

### 5.1 段階別推進計画（あなたが働く病院での展開案）

#### Phase 1：準備期（0-3ヶ月）

**目的**: 内製化の可能性を検証、リーダーシップ獲得

**アクション**:

   - 「最初は小さく、1つの機能から」という段階的アプローチ

   - Microsoft Power Apps / Claris FileMaker などを試用
   - 実際にプロトタイプを作成
   - 「本当にできるか」を検証

3. 医療スタッフからの要件収集
   - 「手作業が多い業務」「時間がかかる業務」をヒアリング
   - 優先順位を決定（最初は「小さい成功」から）

#### Phase 2：実装期（3-9ヶ月）

**目的**: 最初の成功事例を作る

**アクション**:
1. パイロットプロジェクト実施
   - 1つの部門・1つの業務に絞る（例：患者受付業務 など）
   - ローコードツール + AI支援で開発
   - 3-4ヶ月で完成を目指す

2. 医療スタッフとの密な連携
   - 週1回のコミュニケーション
   - 実装途中でも「試用・フィードバック」を繰り返す
   - 「医療スタッフ = 開発チーム の一員」という姿勢

3. 成功事例の可視化
   - 「この業務が月30時間短縮された」を数字で示す
   - 医療スタッフからの喜びの声を記録
   - 全院にシェア

#### Phase 3：拡大期（9-18ヶ月）

**目的**: 複数部門への展開、市民開発の育成開始

**アクション**:
1. 次のプロジェクト実施
   - Phase 2の成功に続いて、次の業務を内製化
   - 「複数部門の医療スタッフが開発に参加」する体制に

2. 市民開発者の育成開始
   - ローコードツールのトレーニング実施
   - 医療スタッフの中から「開発に興味がある」人を育成

3. AI開発支援の活用拡大
   - Amazon Q など AI ツールを本格導入
   - 複雑なロジック部分も AI 支援で実装可能に

#### Phase 4：成熟期（18ヶ月以降）

**目的**: 継続的な改善・イノベーション

**アクション**:
1. 組織が自走する状態に
   - 医療スタッフが自ら「このシステムがあれば便利」と提案
   - 一部は医療スタッフ自身が開発

2. 新しい挑戦

   - 診療の質向上への貢献
