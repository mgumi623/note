## 1. エグゼクティブサマリー

### 日本の医療機関を取り巻くサイバー脅威の現状

日本の医療機関に対するランサムウェア攻撃は急激に増加しており、2025年1月～10月の公式確認件数は85件（前年同期比250%増）に達しています。被害の70%は200床以下の中小規模病院に集中しており、せいわ会グループの22病院も標的となり得る規模帯に該当します。

攻撃による平均システム停止期間は**約2週間～3ヶ月**、復旧費用は**数千万円～2億円超**に及び、医療機関の経営に甚大な影響を与えています。

### S-BOTの総合セキュリティ評価

| 評価カテゴリ | スコア | 判定 |
|:---|:---:|:---:|
| アーキテクチャセキュリティ | 9.0 / 10 | 優秀 |
| 認証・認可 | 8.5 / 10 | 良好 |
| データ保護 | 8.0 / 10 | 良好 |
| コードセキュリティ | 8.5 / 10 | 良好 |
| ランサムウェア特有の耐性 | 7.5 / 10 | 良好（改善余地あり） |
| **総合スコア** | **8.3 / 10** | **良好** |

S-BOTは、クラウドネイティブアーキテクチャ（Vercel + Supabase）の採用により、従来型のオンプレミス医療システムと比較して**本質的にランサムウェアに対する高い耐性**を備えています。ただし、運用面やインシデント対応計画においては改善の余地があります。

### 主要な推奨事項（上位3件）

1. **インシデント対応計画の策定と訓練**（優先度：最高）
2. **バックアップの復元テスト定期実施**（優先度：高）
3. **サプライチェーンセキュリティの強化**（優先度：高）

## 2. 脅威環境分析

### 2.1 日本の医療機関へのランサムウェア攻撃の動向

#### 統計データ（2024-2025年）

| 指標 | 数値 |
|:---|:---|
| 2025年1-10月 公式確認件数 | 85件 |
| 前年同期比増加率 | 250% |
| 未報告を含む推定件数 | 150件超 |
| 被害の70%を占める規模 | 200床以下の中小病院 |
| 救急受入停止の平均期間 | 72時間 |
| 手術延期累計 | 3,000件超 |
| 影響を受けた患者数推計 | 50万人 |

医療機関が狙われる理由は明確です。

- **情報の価値が高い**: 患者の個人情報・医療情報はダークウェブで高値で取引される
- **業務停止の影響が大きい**: 人命に関わるため、身代金を支払う動機が強い
- **セキュリティ投資が不足**: IT専門人材の不足と予算制約
- **レガシーシステムの残存**: VPN装置やRDPの脆弱性が放置されがち

#### 主要な攻撃者グループ

| グループ名 | 手法 | 日本での活動 |
|:---|:---|:---|
| LockBit | VPN脆弱性の悪用、二重脅迫 | 半田病院（2021年）等 |
| Qilin (キリン) | データ窃取+暗号化の二重脅迫 | 宇都宮セントラルクリニック（2025年） |
| 不明（国際犯罪組織） | RDP/VPN経由の侵入 | 多数の中小病院 |

### 2.2 主要攻撃事例の詳細分析

#### 事例1: 岡山県精神科医療センター（2024年5月）

| 項目 | 内容 |
|:---|:---|
| **発生日** | 2024年5月19日 |
| **被害規模** | 最大40,000人分の個人情報流出 |
| **攻撃経路** | 保守用SSL-VPN装置の脆弱性 |
| **根本原因** | VPN装置のID/パスワードが「administrator/P@ssw0rd」で全端末共通 |
| **復旧期間** | 仮復旧：約2週間、完全復旧：約3ヶ月 |

**詳細分析**: 2018年の設置以降VPN装置の脆弱性が一度も修正されておらず、2023年6月に全国組織から脆弱性通知を受けていたにもかかわらず対応が棚上げされていました。調査報告書では「人災」と断定されています。

#### 事例2: DIC宇都宮セントラルクリニック（2025年2月）

| 項目 | 内容 |
|:---|:---|
| **発生日** | 2025年2月10日（公表：2月18日） |
| **被害規模** | 最大約300,000件の個人情報漏洩の可能性 |
| **攻撃者** | Qilin（キリン）ランサムウェアグループ |
| **攻撃手法** | 二重脅迫（データ暗号化+情報公開脅迫） |
| **結果** | 身代金支払い拒否 → ダークウェブに情報公開 |

**詳細分析**: 電子カルテ・院内システムが完全に使用不能となり、救急・外来の受入制限が発生しました。Qilinグループは身代金要求を拒否された後、窃取したデータをダークウェブ上に公開しており、二重脅迫型攻撃の典型例です。

#### 事例3: 国分生協病院（2024年2月）

| 項目 | 内容 |
|:---|:---|
| **発生日** | 2024年2月27日 |
| **被害規模** | 画像管理サーバーのPDFデータ暗号化（30TB以上） |
| **攻撃経路** | 認証なしでリモート接続可能な保守用ネットワーク機器 |
| **根本原因** | セキュリティソフト未導入 + 認証なしRDP |
| **復旧期間** | 救急・外来再開まで約3週間 |

**詳細分析**: 事業者用ネットワーク機器において認証なしで病院端末にリモート接続可能な設定になっており、さらに画像管理サーバーにはセキュリティソフトが導入されていないという二重の問題がありました。

#### 事例4: つるぎ町立半田病院（2021年10月）

| 項目 | 内容 |
|:---|:---|
| **発生日** | 2021年10月31日 |
| **被害規模** | 電子カルテシステム全面停止、約85,000人分の診療データ影響 |
| **攻撃者** | LockBit 2.0 |
| **攻撃経路** | VPN装置の脆弱性（CVE-2018-13379） |
| **復旧費用** | 約2億数千万円 |
| **復旧期間** | 約2ヶ月 |

**詳細分析**: 日本の医療機関へのランサムウェア攻撃の転機となった事例です。「閉域網だから安全」という誤認のもとVPN脆弱性が2年以上放置され、認証情報がダークウェブに流出していました。ベンダー依存のセキュリティ体制の危険性を浮き彫りにしました。

### 2.3 攻撃パターンの共通点

4つの事例から抽出された共通の攻撃パターンは以下の通りです。

```
攻撃の典型フロー:

  1. 初期侵入
     └─ VPN脆弱性 / 認証なしRDP / 弱いパスワード

  2. 内部探索
     └─ 共通管理者パスワードによる横展開（ラテラルムーブメント）

  3. データ窃取
     └─ 患者情報・診療データの外部転送

  4. 暗号化
     └─ 電子カルテ・業務システムの暗号化

  5. 脅迫
     └─ 身代金要求 + データ公開脅迫（二重脅迫）
```

**共通する脆弱点**:
- VPN/RDP等のリモートアクセス機器の脆弱性放置
- 弱い認証（デフォルトパスワード、共通パスワード）
- ネットワークセグメンテーションの不備
- バックアップの不備または同一ネットワーク上への配置
- セキュリティ監視の欠如
- 「閉域網だから安全」という誤った認識

## 3. S-BOTのランサムウェア耐性評価

### 3.1 評価方法

S-BOTのソースコード、アーキテクチャ設計、セキュリティ実装を静的分析し、5つのカテゴリで10点満点のスコアリングを行いました。評価基準は、上記の実際の攻撃事例で悪用された脆弱性への耐性を重視しています。

### 3.2 カテゴリ別評価

#### カテゴリ1: アーキテクチャセキュリティ — 9.0 / 10（優秀）

| 評価項目 | 状態 | 詳細 |
|:---|:---:|:---|
| クラウドネイティブ設計 | 対策済 | Vercel（サーバーレス）+ Supabase（マネージドDB） |
| サーバーレス実行環境 | 対策済 | 攻撃者がOS/ファイルシステムに直接アクセスする経路なし |
| ネットワーク分離 | 対策済 | Vercelプラットフォームによる自動的なネットワーク分離 |
| VPN/RDPの排除 | 対策済 | オンプレミスのVPN/RDP機器が存在しない |
| HTTPS強制 | 対策済 | Vercelによる自動SSL/TLS、HSTS有効 |
| セキュリティヘッダー | 対策済 | CSP（nonce+strict-dynamic）、X-Frame-Options等を包括的に実装 |

**評価根拠**: S-BOTの最大の強みは、クラウドネイティブ（サーバーレス）アーキテクチャを採用していることです。上記4事例すべてにおいて攻撃の起点となった「オンプレミスのVPN装置」「認証なしRDP」「管理者パスワードの共有」といった脆弱点が、S-BOTには構造的に存在しません。

攻撃者がファイルシステムに直接アクセスしてランサムウェアを実行する経路がないため、従来型の「ファイル暗号化型」ランサムウェアに対して本質的に高い耐性を持ちます。

**コード根拠**:
- `src/proxy/security.ts` — CSP（nonce+strict-dynamic）、HSTS、X-Frame-Options等の包括的セキュリティヘッダー
- `next.config.ts` — `poweredByHeader: false`、`productionBrowserSourceMaps: false` によるフィンガープリント対策

**減点要因（-1.0）**: サプライチェーン攻撃（npm依存パッケージの侵害等）への対策が明示的に文書化されていない。

---

#### カテゴリ2: 認証・認可 — 8.5 / 10（良好）

| 評価項目 | 状態 | 詳細 |
|:---|:---:|:---|
| MFA（多要素認証） | 対策済 | TOTP方式のMFA実装、ミドルウェアレベルでの強制 |
| セッション管理 | 対策済 | Supabase Auth + JWT、httpOnly Cookie |
| CSRF保護 | 対策済 | ダブルサブミット方式 + タイミング安全比較 |
| RBAC（ロールベースアクセス制御） | 対策済 | `super_admin` / `hospital_admin` / `staff` / `viewer` の4階層 |
| テナント分離 | 対策済 | `hospital_id` によるRLSポリシー + アプリケーション層チェック |
| レート制限 | 対策済 | 認証エンドポイント含む全APIにレート制限実装 |
| パスワードポリシー | 対策済 | Supabase Auth標準 + zodバリデーション |

**評価根拠**: 岡山の事例では「administrator/P@ssw0rd」という弱いパスワードが全端末で共有されていました。S-BOTでは以下の多層防御が実装されています。

1. **MFA強制**: `src/proxy/middleware/mfa.ts` でミドルウェアレベルでAAL（Authentication Assurance Level）を検証し、MFA未設定ユーザーを自動的にMFAセットアップ画面へリダイレクト
2. **CSRF保護**: `src/lib/security/csrf-protection.ts` でEdge Runtime対応のダブルサブミット方式を実装、`timingSafeEqual` によるタイミング攻撃対策済
3. **RBAC + RLS**: ロールベースのアクセス制御がAPIルート層とデータベース層の二重で適用

**コード根拠**:
- `src/proxy/middleware/mfa.ts` — AAL検証とMFA強制リダイレクト
- `src/lib/security/csrf-protection.ts` — CSRF保護（Web Crypto API使用、Edge対応）
- `src/lib/security/rbac-guard.ts` / `rbac-utils/` — 包括的なRBAC実装
- `src/lib/security/api-auth.core.ts` — プロキシ認証署名検証

**減点要因（-1.5）**: 管理者アカウントのパスワードローテーションポリシーが明示されていない。アカウントロックアウト閾値の文書化がない。

---

#### カテゴリ3: データ保護 — 8.0 / 10（良好）

| 評価項目 | 状態 | 詳細 |
|:---|:---:|:---|
| 保存時暗号化 | 対策済 | Supabase（PostgreSQL）のディスク暗号化 |
| 通信暗号化 | 対策済 | TLS 1.3、HSTS preload |
| アプリケーション層暗号化 | 対策済 | AES-256-GCM（`EncryptionService`） |
| RLS（Row Level Security） | 対策済 | 全業務テーブルに `hospital_id` ベースのRLS |
| 入力検証 | 対策済 | zodスキーマ + インジェクション防止 |
| ファイルアップロード検証 | 対策済 | MIME検証、マジックバイト検証、サニタイズ |
| ログのPII保護 | 対策済 | 機微情報のマスキング処理 |

**評価根拠**: 宇都宮の事例では窃取されたデータがダークウェブに公開される「二重脅迫」が行われました。S-BOTでは以下のデータ保護策が実装されています。

1. **暗号化の多層実装**: `src/lib/security/encryption.ts` でAES-256-GCM暗号化サービスを提供。PBKDF2による鍵導出（100,000反復）も実装
2. **RLSによるテナント分離**: データベースレベルで病院間のデータ分離を強制
3. **インジェクション防止**: `src/lib/security/injection-prevention.ts` でSQLi、XSS、コマンドインジェクション等を多層的に検出・防御
4. **プロンプトインジェクション対策**: `src/lib/security/prompt-injection/` でAI機能への入力攻撃も防御

**コード根拠**:
- `src/lib/security/encryption.ts` — AES-256-GCM暗号化サービス
- `src/lib/security/injection-prevention*.ts` — 包括的インジェクション防止
- `src/lib/security/file-security*.ts` — ファイルアップロードセキュリティ
- `src/lib/security/prompt-injection/` — AIプロンプトインジェクション対策

**減点要因（-2.0）**: バックアップの復元テスト手順が文書化されていない。データ分類ポリシー（何がどのレベルの保護を必要とするか）の明示的な文書がない。

#### カテゴリ4: コードセキュリティ — 8.5 / 10（良好）

| 評価項目 | 状態 | 詳細 |
|:---|:---:|:---|
| TypeScript strict | 対策済 | `any` 禁止、`exactOptionalPropertyTypes` 有効 |
| ESLint セキュリティルール | 対策済 | no-console、制限付きインポート |
| 依存関係監査 | 対策済 | `npm audit` スクリプト |
| SonarQube SAST | 対策済 | OWASP Top 10 全カバー |
| シークレット検出 | 対策済 | Gitleaks + カスタムスキャン |
| テストカバレッジ | 対策済 | 5,462テスト、Statement 88.58% |
| セキュリティモニター | 対策済 | `security-monitor.ts` によるリアルタイム監視 |

**評価根拠**: S-BOTは高い品質のセキュリティコード実装を維持しています。

1. **静的解析の多層実行**: ESLint + TypeScript strict + SonarQube + Gitleaksの4層
2. **セキュリティ専用コード**: `src/lib/security/` に80以上のセキュリティ関連ファイル
3. **高いテストカバレッジ**: 5,462テスト、88.58%のStatement カバレッジ
4. **包括的な入力検証**: `src/lib/security/input-validation*.ts` による多段階検証

**減点要因（-1.5）**: Branches カバレッジが76.37%（目標80%未満）。npm依存パッケージの自動脆弱性アラート設定の確認が必要。

#### カテゴリ5: ランサムウェア特有の耐性 — 7.5 / 10（良好、改善余地あり）

| 評価項目 | 状態 | 詳細 |
|:---|:---:|:---|
| ファイル暗号化攻撃への耐性 | 対策済 | サーバーレス環境のため永続ファイルシステムなし |
| DB暗号化攻撃への耐性 | 部分対策 | SupabaseマネージドDBだがSupabaseアカウント侵害リスクあり |
| バックアップ戦略 | 部分対策 | Supabaseの自動バックアップ依存 |
| インシデント対応計画 | 未対策 | 文書化されたIRPが確認できない |
| 事業継続計画（BCP） | 未対策 | ランサムウェア想定のBCPが確認できない |
| サプライチェーン保護 | 部分対策 | npm audit実施だがDependabot未確認 |
| 二重脅迫への対策 | 部分対策 | データ暗号化はあるが流出時の対応計画なし |

**評価根拠**: S-BOTはクラウドネイティブ設計により従来型ランサムウェアに対して構造的に強いですが、以下の新しい脅威への対策が不十分です。

1. **サプライチェーン攻撃**: npmパッケージの侵害によりビルド時またはランタイムに悪意のコードが実行されるリスク
2. **クラウドアカウント侵害**: Vercel/Supabaseの管理者アカウントが侵害された場合の影響
3. **二重脅迫**: データが窃取された場合の対応計画（通知義務、法的対応、広報対応）
4. **インシデント対応**: 文書化されたインシデント対応手順、連絡体制が確認できない

**減点要因（-2.5）**: インシデント対応計画（IRP）の不在が最大の減点要因。BCPの不在。バックアップ復元テストの未実施。

## 4. 実事例から学ぶリスクシナリオ

### 4.1 岡山のケース（VPN脆弱性）とS-BOTの対策状況

| 攻撃要素 | 岡山の状況 | S-BOTの状況 | リスク |
|:---|:---|:---|:---:|
| VPN装置の脆弱性 | 2018年以降未パッチ | VPN装置なし（Vercel） | **排除済** |
| デフォルトパスワード | administrator/P@ssw0rd | Supabase Auth + MFA | **排除済** |
| 共通管理者パスワード | 全端末で同一 | 個別ユーザー認証 + RBAC | **排除済** |
| 内部横展開 | 共通パスワードで全端末アクセス | テナント分離 + RLS | **排除済** |

**S-BOTで同様の攻撃が成功する可能性**: **極めて低い**（0.5/10）

S-BOTにはオンプレミスのVPN装置が存在せず、全てのアクセスはHTTPS経由でVercelのエッジネットワークを通過します。物理的な攻撃面（アタックサーフェス）が根本的に異なります。

---

### 4.2 宇都宮のケース（二重脅迫）とS-BOTの対策状況

| 攻撃要素 | 宇都宮の状況 | S-BOTの状況 | リスク |
|:---|:---|:---|:---:|
| サーバーへの直接侵入 | 成功 | サーバーレスのため不可 | **排除済** |
| データ窃取 | 30万件の個人情報 | RLS + 暗号化で保護 | **低** |
| データの一括エクスポート | 可能だった | RLSでテナント単位に制限 | **低** |
| 身代金支払い拒否後の公開 | 実行された | 対応計画なし | **中（運用面）** |

**S-BOTで同様の攻撃が成功する可能性**: **低い**（2.0/10）

直接侵入は困難ですが、万一のデータ流出時の対応計画（個人情報保護委員会への報告、患者への通知、広報対応）が整備されていない点は改善が必要です。RLSにより攻撃者が全病院のデータを一度に窃取することは困難ですが、単一テナントのデータ流出リスクは残存します。

### 4.3 国分生協のケース（認証なしRDP）とS-BOTの対策状況

| 攻撃要素 | 国分生協の状況 | S-BOTの状況 | リスク |
|:---|:---|:---|:---:|
| 認証なしリモート接続 | 保守機器経由で可能 | 全接続に認証必須 | **排除済** |
| セキュリティソフト未導入 | サーバーに未導入 | マネージドプラットフォーム | **排除済** |
| ネットワーク分離の不備 | 保守網と業務網が未分離 | Vercelによる自動分離 | **排除済** |

**S-BOTで同様の攻撃が成功する可能性**: **極めて低い**（0.3/10）

S-BOTの環境には「認証なしでリモート接続可能な機器」が存在する余地がありません。

### 4.4 S-BOTに対して想定される攻撃シナリオ

S-BOTの構造を考慮した場合、従来型のランサムウェア攻撃は効果が限定的です。ただし、以下の攻撃シナリオは注意が必要です。

**シナリオA: サプライチェーン攻撃（リスク: 中）**
```
1. npmパッケージに悪意のコードが混入
2. ビルド時にマルウェアがデプロイ
3. ユーザーセッション情報の窃取
4. 窃取したセッションでデータにアクセス
```
対策状況: `npm audit` + SonarQubeは実施済だが、Dependabot/Renovateによる自動監視の確認が必要

**シナリオB: クラウドアカウント侵害（リスク: 中）**
```
1. Vercel/Supabase管理者のフィッシング
2. 管理コンソールへの不正アクセス
3. 環境変数（シークレット）の窃取
4. Service Role Keyを使ったRLSバイパス
```
対策状況: Google Auth 2FAが有効（推定）だが、最小権限の原則の適用確認が必要

**シナリオC: 内部犯行（リスク: 低～中）**
```
1. 正規アカウントを持つ内部関係者
2. 権限を超えたデータアクセス試行
3. RLSをバイパスするAPIの悪用
```
対策状況: RBAC + RLSの二重制御は実装済。監査ログの網羅性確認が必要

## 7. 結論

### S-BOTの総合的なランサムウェア耐性

S-BOTは、**総合スコア 8.3 / 10（良好）**という高い水準のセキュリティを達成しています。特に以下の点が際立っています。

**S-BOTの強み（従来型医療システムとの比較）**:

1. **クラウドネイティブ設計による構造的優位性**: 直近の国内医療機関への攻撃事例4件すべてにおいて悪用された「VPN脆弱性」「認証なしRDP」「共通管理者パスワード」が、S-BOTには構造的に存在しない
2. **多層防御の実装**: 認証（MFA）→ 認可（RBAC）→ データ保護（RLS + 暗号化）→ 入力検証（zod + インジェクション防止）の4層防御
3. **高品質なセキュリティコード**: 80以上のセキュリティ関連ファイル、5,462テスト、88.58%のカバレッジ

**改善すべき領域**:

主に**運用面**に集中しており、技術的な脆弱性は限定的です。

1. インシデント対応計画（IRP）の策定
2. バックアップ復元テストの定期実施
3. サプライチェーン監視の自動化
4. 事業継続計画（BCP）の策定

### せいわ会グループの経営層へのメッセージ

せいわ会グループの経営層の皆様へ、以下の3点をお伝えします。

**1. S-BOTは従来型システムと比較して本質的に安全です**

2024～2025年に発生した医療機関へのランサムウェア攻撃は、いずれもオンプレミスのVPN/RDP等の脆弱性が起点でした。S-BOTはクラウドネイティブ設計を採用しており、これらの攻撃経路が構造的に存在しません。22病院の業務データがSupabaseのRLSポリシーによって病院単位で分離されている点も、被害の局所化に寄与します。

**2. ただし「安全」は「何もしなくていい」という意味ではありません**

岡山や半田の事例が示すように、最大のリスクは技術ではなく**「対応の遅れ」と「準備の不足」**です。S-BOTの技術的なセキュリティは高い水準にありますが、インシデント発生時の対応計画がなければ、被害は不必要に拡大します。特に、個人情報保護法では漏洩時の72時間以内の報告義務があり、準備なしの対応は法的リスクにもつながります。

**3. 最優先の投資は「計画と訓練」です**

推奨する対策の多くは高額な投資を必要としません。インシデント対応計画の策定、バックアップ復元テスト、スタッフ研修は、いずれも人件費のみで実施可能です。半田病院の復旧費用が2億円超であったことを考えれば、予防的な投資の費用対効果は極めて高いと言えます。

### 継続的なセキュリティ改善の重要性

サイバーセキュリティは「一度整備すれば完了」するものではありません。攻撃者の手法は常に進化しており、2021年のVPN脆弱性悪用から2025年の二重脅迫型攻撃への変遷が示すように、脅威は年々高度化しています。

S-BOTの開発チームは、TypeScript strict、ESLint 9、SonarQube、5,462テストという高い品質基準を維持しており、コードレベルでのセキュリティ意識は極めて高いと評価できます。この技術的基盤の上に、運用面での対策を追加することで、せいわ会グループの22病院の業務と患者データを、進化する脅威から継続的に保護することが可能です。

## 8. ケーススタディ: 日本医科大武蔵小杉病院ランサムウェア攻撃（2026年2月）

### これは何か（事件の定義）

2026年2月9日に発生した、日本医科大学武蔵小杉病院（神奈川県川崎市）に対する大規模なランサムウェア攻撃事件。

**ランサムウェアとは**: コンピュータウイルスの一種で、感染するとファイルを暗号化して使えなくし、復号（元に戻すこと）と引き換えに身代金（Ransom）を要求する悪質なプログラム。

本事件では約1万人分の患者個人情報が漏洩し、攻撃者から152億円という巨額の身代金を要求された、日本の医療機関を狙ったサイバー攻撃の中でも特に深刻なケースとなった。

### なぜ重要なのか

#### 1. 医療機関のサイバーセキュリティの脆弱性が露呈

医療機関は現在、**全産業の中で最も攻撃を受けやすいセクター**となっており、攻撃成功率も他業界の約3倍に達している。この事件は、日本の医療機関のセキュリティ対策が十分でないことを示す象徴的な事例となった。

#### 2. 患者の個人情報保護の課題

病院は患者の氏名、住所、電話番号、病歴など、極めて機密性の高い情報を大量に保有している。これらの情報が漏洩すると：

- **個人のプライバシーが侵害される**: 病歴などセンシティブな情報が流出する可能性
- **詐欺などの二次被害のリスク**: 漏洩した個人情報を使った詐欺電話などの被害が発生する可能性
- **病院への信頼が失墜**: 患者が安心して受診できなくなる

#### 3. 医療の継続性への脅威

今回は診療業務への影響は最小限だったが、ランサムウェア攻撃によって医療情報システムが完全に停止すれば：

- **電子カルテが使えなくなる**: 患者の治療歴や投薬情報が確認できない
- **予約システムが停止**: 新規患者の受け入れができない
- **最悪の場合、診療停止**: 実際に過去には診療を停止した病院の事例もある

人の命に関わる医療機関だからこそ、「システムが止まると困る」という弱みがあり、攻撃者に狙われやすい。

### 事件の詳細な経緯

#### 攻撃の発覚まで（2026年2月9日）

##### 午前1時50分頃: 異常の検知

病棟でナースコール端末が動作不良を起こす。

**ナースコールとは**: 病室のベッドに設置されているボタンで、患者が看護師を呼ぶための装置。患者の命に直結する重要なシステム。

この動作不良により、夜間の医療スタッフが異常を覚知した。深夜の時間帯での発覚は、攻撃者が検知されにくい時間帯を狙った可能性がある。

##### ベンダー調査によるランサムウェア検出

ナースコールシステムのベンダー（メーカー）が調査を実施したところ、サーバーがランサムウェア攻撃を受けていることが判明。

**攻撃を受けたシステム**: ナースコールシステムサーバー 3台

##### 即座の封じ込め対応

病院は迅速に以下の対応を実施：

1. **当該システムの遮断**: ナースコールシステムをネットワークから切り離す
2. **関連ネットワークの遮断**: 他のシステムへの感染拡大を防ぐ
3. **関係機関への報告**:
   - 文部科学省（大学附属病院のため）
   - 厚生労働省（医療機関を管轄）
   - 所轄警察（犯罪として捜査依頼）

この迅速な対応により、他の医療情報システムへの感染拡大を防ぐことができた。

#### 公式発表と対応（2月13日以降）

##### 第1報の公表（2月13日）

病院が公式サイトで事件を公表。透明性を重視し、患者と社会に対して情報開示を行った。

神奈川県警に被害届を提出。サイバー犯罪として正式に捜査が開始された。

1. **ランサムウェアの特定**: 攻撃に使用されたランサムウェアの種類を特定
2. **最新のパターンファイル取得**: ウイルス対策ソフト会社から最新の定義ファイルを入手
3. **院内全域でウイルス駆除**: すべてのシステムを対象にスキャンと駆除を実施

### 被害状況の詳細

#### 漏洩した個人情報

- **対象人数**: 約1万人（確認された人数）
- **漏洩した情報の項目**:
  - 氏名
  - 性別
  - 住所
  - 電話番号
  - 生年月日
  - 患者ID

**これが意味すること**:
- これらの情報があれば、「〇〇病院の患者」として個人を特定できる
- 住所や電話番号を使った詐欺などの二次被害のリスクがある
- 病院に通院していたという事実そのものがプライバシーに関わる

#### 漏洩しなかった情報

- **カルテ（診療記録）**: どんな病気で、どんな治療を受けたかの記録
- **クレジットカード情報**: 決済情報

**なぜこれらは守られたのか**:
ナースコールシステムのサーバーが攻撃されたため、電子カルテシステムなど他のシステムのデータは無事だった。ネットワークを分離していた（セグメンテーション）ことが被害拡大を防いだ。

#### 診療業務への影響

- **他の医療情報システム**: 影響なし（正常稼働）
- **病院業務**: 通常通り実施
- **ナースコールシステム**: 代替手段で対応（詳細は不明だが、おそらく手動での巡回や内線電話などで対応）

**これが意味すること**:
今回は運良く診療を継続できたが、もし電子カルテシステムが攻撃されていたら診療停止の可能性もあった。

### 身代金要求の実態

#### 要求額

**1億ドル = 約152億円**

**この額がいかに巨額か**:
- 一般的なランサムウェアの身代金は数百万円〜数千万円程度
- 152億円は通常の数百倍から数千倍の額
- 大学病院の年間予算規模を考えても支払い不可能な金額

#### 病院の対応

**「毅然とした態度で臨む」として身代金は支払わず**

**これが正しい判断である理由**:
1. **支払っても復旧の保証はない**: 攻撃者が約束を守る保証はない
2. **犯罪を助長する**: 支払うことで、さらなる攻撃を誘発する
3. **他の病院も標的にされる**: 「病院は金を払う」という認識が広がる

日本政府も身代金の支払いは推奨していない。

### 攻撃の原因 - なぜ侵入されたのか

#### 侵入経路: 医療機器保守用VPN装置

**VPN（Virtual Private Network）とは**:
離れた場所から病院内のネットワークに安全に接続するための仕組み。医療機器のメーカーが、遠隔地から病院内の機器をメンテナンスするために使用する。

**なぜVPNが狙われたのか**:
1. **外部からアクセス可能**: インターネット経由で接続できる
2. **病院内のネットワークに直結**: VPNを突破すれば院内システムにアクセスできる
3. **セキュリティが甘い場合が多い**: 医療機器保守用のVPNは、利便性を優先してセキュリティが疎かになりがち

#### 具体的な脆弱性

**VPNのパスワードが解読されやすいものだった可能性**

**解読されやすいパスワードの例**:
- 短いパスワード（8文字以下）
- 辞書に載っている単語（"password", "hospital123"など）
- 数字の連番（"12345678"など）
- デフォルトパスワードのまま（機器の初期設定から変更していない）

**攻撃者の手口（推測）**:
1. **総当たり攻撃（ブルートフォース）**: 可能性のあるパスワードを片っ端から試す
2. **辞書攻撃**: よく使われるパスワードのリストを使って試す
3. **既知の脆弱性を悪用**: VPN装置の古いバージョンに存在するセキュリティホールを突く

#### セキュリティ対策の不備

考えられる対策の不備：

1. **多要素認証（2FA）の未導入**: パスワードだけでなく、スマホアプリの認証コードなど複数の方法で認証する仕組みが無かった
2. **パスワードポリシーの不備**: 強固なパスワードの使用を強制していなかった
3. **VPN装置のアップデート不足**: 古いバージョンのまま使用し、既知の脆弱性が放置されていた
4. **アクセスログの監視不足**: 不審なアクセス試行を検知できなかった

### なぜ医療機関が狙われるのか - 構造的な問題

#### 1. 機密性の高い個人情報を大量に保有

病院が保有する情報：
- **氏名、住所、電話番号**: 基本的な個人情報
- **病歴**: どんな病気にかかったか（非常にセンシティブ）
- **投薬情報**: どんな薬を飲んでいるか
- **検査結果**: 血液検査、画像診断など
- **家族構成**: 緊急連絡先など

**これらの価値**:
- ダークウェブ（闇市場）で高額で取引される
- 詐欺に悪用できる（「〇〇病院から」と名乗る詐欺など）
- 個人を脅迫する材料になる（「病歴を公開されたくなければ金を払え」）

#### 2. システム停止が許されない = 身代金を支払いやすい

**医療は止められない**:
- 病院は24時間365日稼働している
- 電子カルテが使えないと診療ができない
- 予約システムが止まると新規患者を受け入れられない
- 緊急患者の受け入れができないと命に関わる

**攻撃者の心理**:
「病院は人命に関わるから、身代金を払ってでもシステムを復旧させるだろう」

実際、海外では身代金を支払った病院も存在する。

#### 3. セキュリティ対策が遅れている

**なぜ遅れているのか**:

##### 予算の制約
- 病院経営は厳しい（74.6%が医業赤字）
- セキュリティ対策にかける予算が限られる
- 「医療機器や人件費が優先、セキュリティは後回し」になりがち

##### 人材の不足
- 医療ITに詳しい人材が少ない
- セキュリティ専門家がいない（医師や看護師が片手間で対応）
- 外部の専門業者に依頼するコストが高い

##### レガシーシステム（古いシステム）の存在
- 医療機器は10年、20年と長期間使用される
- 古いOSやソフトウェアを使い続けている
- アップデートすると医療機器が動かなくなるリスク

##### 複雑なネットワーク構成
- 電子カルテ、検査システム、画像システム、会計システムなど多数のシステムが連携
- 医療機器メーカーごとに保守用のVPNが存在
- 全体を統合的に管理するのが困難

### 他の医療機関の被害事例（2025年）

#### 医療法人DIC 宇都宮セントラルクリニック（2025年2月）

- **被害**: ランサムウェア攻撃
- **漏洩情報**: 最大約30万人分の個人情報
- **影響**: 武蔵小杉病院の3倍の規模の漏洩

**これが意味すること**:
医療機関を狙ったランサムウェア攻撃は2025年から2026年にかけて増加傾向にあり、武蔵小杉病院の事件は決して特殊なケースではない。

#### 過去の海外事例

- **米国の病院**: ランサムウェア攻撃により診療を数週間停止
- **ドイツの病院**: 電子カルテが使えず、患者を他の病院に転送中に死亡（間接的な被害）

**日本でも同様の事態が起こりうる**という危機感が必要。

### 厚生労働省の対策とガイドライン

#### サイバーセキュリティ対策チェックリスト（2025年5月14日公表）

厚生労働省が医療機関向けに公表したチェックリスト。主な項目：

##### 1. 強固なパスワード設定

**具体的には**:
- 12文字以上のパスワード
- 英大文字、英小文字、数字、記号を組み合わせる
- 辞書に載っている単語を使わない
- 定期的に変更する

**NG例**: "hospital2026", "kosugi123"
**OK例**: "K#9mZ$2pL!7q"（ランダムな文字列）

##### 2. USB等の接続制限

**なぜUSBが危険か**:
- ウイルスに感染したUSBメモリを挿すだけで感染する
- 職員が無意識に感染したUSBを持ち込む可能性
- 悪意のある第三者が意図的にウイルス入りUSBを置いていく手口もある

**対策**:
- 業務用以外のUSBメモリの使用を禁止
- USBポートを物理的に塞ぐ
- USBの接続を監視・制御するソフトを導入

##### 3. 2要素認証（2FA）の導入

**2要素認証とは**:
ログインする際に、2つの方法で本人確認をする仕組み。

**例**:
1. パスワードを入力（知識要素）
2. スマホアプリに表示される6桁のコードを入力（所持要素）

**なぜ安全か**:
- パスワードが漏れても、スマホを持っていなければログインできない
- 総当たり攻撃が事実上不可能になる

**導入目標**: 2027年度までに医療機関での導入を推進

#### 実効的な防御体制の構築

厚生労働省のチェックリストは必要だが、**形式的に「やっているふり」では意味がない**。実効性のある対策が重要：

##### 1. オフラインバックアップ

**オフラインバックアップとは**:
ネットワークから切り離された状態でデータをバックアップする方法。

**具体的には**:
- 外付けHDDにバックアップした後、HDDを物理的に取り外す
- テープバックアップ（古典的だが確実）
- クラウドバックアップ + 定期的なオフラインコピー

**なぜ重要か**:
- ランサムウェアはネットワーク上のバックアップも暗号化する
- オフラインなら、ランサムウェアが到達できない
- 身代金を払わなくてもデータを復旧できる

##### 2. ネットワークセグメンテーション

**ネットワークセグメンテーションとは**:
病院内のネットワークを複数の区画（セグメント）に分割し、相互のアクセスを制限する方法。

**具体的には**:
- 電子カルテシステム用ネットワーク
- 検査システム用ネットワーク
- 会計システム用ネットワーク
- インターネット接続用ネットワーク
- これらを分離し、必要最小限の通信のみ許可

**効果**:
- 今回の武蔵小杉病院の事例では、ナースコールシステムが攻撃されても電子カルテは無事だった
- これはセグメンテーションが機能していた可能性がある
- 1つのシステムが感染しても、他のシステムへの拡散を防ぐ

##### 3. 職員教育

**人間が最大の脆弱性**:
どんなに技術的対策をしても、職員が不注意なら意味がない。

**教育すべき内容**:
- **フィッシングメールの見分け方**:
  - 送信者のアドレスを確認
  - 不自然な日本語に注意
  - リンクをクリックする前にURLを確認
- **不審なUSBメモリを挿さない**
- **強固なパスワードの作成方法**
- **不審なアクセスを見たら報告する**

**定期的な訓練**:
- 模擬フィッシングメールを送って、引っかかった職員を教育
- 年1回のセキュリティ研修を義務化

##### 4. 実践的な復旧訓練

**訓練の重要性**:
実際に攻撃を受けた時、慌てずに対応できるか。

**訓練内容**:
- ランサムウェア感染を想定したシミュレーション
- バックアップからのデータ復旧手順の確認
- 関係機関（警察、厚労省など）への報告手順の確認
- 患者への説明方法の確認

**訓練していないと**:
- パニックになって二次被害を拡大させる
- バックアップの取り方を知らず、データが失われる
- 報告が遅れ、被害が拡大する

### 今後の展望と対策

#### 医療機関が今すぐすべきこと

##### 最優先事項

1. **VPNのセキュリティ強化**:
   - 強固なパスワードに変更
   - 2要素認証の導入
   - VPN装置を最新バージョンにアップデート
   - 不要なVPNは廃止

2. **オフラインバックアップの実施**:
   - 毎日バックアップを取る
   - バックアップメディアを物理的に隔離
   - 定期的に復旧テストを実施

3. **ネットワークセグメンテーション**:
   - 重要なシステムを分離
   - 医療機器保守用ネットワークを一般ネットワークから隔離

##### 中長期的な対策

1. **セキュリティ人材の確保**:
   - 専門家を雇用（難しい場合は外部委託）
   - 既存職員のセキュリティ教育

2. **セキュリティ投資の予算確保**:
   - 「セキュリティはコストではなく投資」という認識
   - 被害を受けた場合の損失（信頼失墜、賠償金など）と比較

3. **システムの近代化**:
   - レガシーシステムの段階的な更新
   - セキュリティを考慮した新システムの導入

#### 政府・業界団体がすべきこと

1. **補助金・支援制度の拡充**:
   - 中小病院はセキュリティ投資の余裕がない
   - 国がセキュリティ対策費用を補助

2. **情報共有の促進**:
   - 攻撃の手口や対策を業界全体で共有
   - 「うちの病院が狙われた」を恥ずかしがらず、他の病院に警告

3. **規制の強化**:
   - 一定以上の規模の医療機関に対し、セキュリティ基準を義務化
   - 違反した場合のペナルティ

#### 患者（一般市民）ができること

1. **病院のセキュリティ対策を確認**:
   - 「この病院はサイバーセキュリティ対策をしていますか？」と質問
   - セキュリティに無関心な病院は選ばない

2. **二次被害への警戒**:
   - 情報漏洩の発表があった場合、詐欺電話などに注意
   - 「〇〇病院から」と名乗る電話は疑う

3. **被害を受けた病院を過度に責めない**:
   - 病院も被害者
   - 攻撃を受けたことを公表し、透明性を保つ病院を評価

### この事件から得られる教訓

#### 1. 「うちの病院は大丈夫」という過信は危険

武蔵小杉病院は日本医科大学の附属病院という大規模病院。それでも攻撃を受けた。

**攻撃者は**:
- 大学病院だろうと町のクリニックだろうと関係なく狙う
- むしろ大病院の方が身代金を支払う余力があると考えて狙う

**すべての医療機関が標的**という認識が必要。

#### 2. セキュリティ対策は「やっているふり」では意味がない

- チェックリストに形式的にチェックを入れるだけでは不十分
- 実際に機能する対策を、継続的に実施する必要がある

**例**:
- バックアップを取っていても、復旧テストをしていないと、いざという時に使えない
- パスワードポリシーがあっても、職員が守らなければ意味がない

#### 3. 医療機関のセキュリティは社会全体の問題

- 病院がサイバー攻撃を受けると、患者が診療を受けられなくなる
- 緊急患者の受け入れができなくなると、命に関わる
- 医療機関のセキュリティは、社会インフラの安全性に直結する

**だからこそ**:
- 病院任せにせず、政府や業界団体が支援
- 患者（国民）もセキュリティ意識を持つ

#### 4. 透明性と迅速な対応が被害を最小化する

武蔵小杉病院は：
- 攻撃を受けた当日に関係機関に報告
- 4日後に公式発表
- 身代金を支払わない方針を明確化

**これにより**:
- 二次被害（他の病院への攻撃）を警告できる
- 患者に注意喚起できる
- 社会の信頼を維持できる

**隠蔽は最悪の選択**:
- 後でバレた時の信頼失墜はより大きい
- 法的な責任を問われる可能性

### まとめ

日本医科大学武蔵小杉病院のランサムウェア攻撃事件は、日本の医療機関が直面するサイバーセキュリティの脆弱性を浮き彫りにした。

**主要なポイント**:

1. **侵入経路はVPN**: 医療機器保守用のVPNが狙われた。強固なパスワードと2要素認証が不可欠。

2. **被害は約1万人**: 個人情報が漏洩したが、迅速な対応で診療業務は継続できた。

3. **身代金152億円を拒否**: 正しい判断。支払いは犯罪を助長する。

4. **医療機関は最も狙われやすい**: 機密情報を持ち、システム停止が許されず、セキュリティ対策が遅れている。

5. **実効性のある対策が必要**: オフラインバックアップ、ネットワークセグメンテーション、職員教育、復旧訓練。

6. **社会全体で取り組むべき課題**: 政府の支援、業界の情報共有、患者の意識向上が必要。

**最も重要なメッセージ**:
「サイバー攻撃は他人事ではない。すべての医療機関が標的になりうる。今すぐ対策を始めるべき。」

この事件を教訓に、日本の医療機関全体がセキュリティレベルを向上させることが、患者の安全と社会の安定につながる。
