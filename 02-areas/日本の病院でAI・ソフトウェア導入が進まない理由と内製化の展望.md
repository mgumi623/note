# 日本の病院でAI・ソフトウェア導入が進まない理由と内製化の展望

> 「Amazon BedrockやAzure OpenAI APIを使えば簡単にAIチャットが作れるのに、なぜ病院では普及しないのか？」という問いへの多面的な調査・考察ノート（2026年2月時点）

---

## 1. 現状：日本の病院のAI導入率

まず数字で現状を把握します。

| 指標 | 数値 | 出典 |
|------|------|------|
| 診断補助AIの導入率 | **7〜11%** | 厚生労働科学研究（2024年） |
| AIを「未導入」の医療機関 | **約8割** | 日経リサーチ調査 |
| ヘルスケア業界の生成AI推進度（業界ランキング） | 2023年3位 → 2024年**9位に後退** | PwC Japan調査 |
| 米国の大規模病院でのAI活用率 | **90〜96%** | IntuitionLabs（2025年） |

つまり、**日本の病院のAI活用率は米国の10分の1以下**という状況です。「簡単なはず」という感覚と現実の大きなギャップには、技術的な問題ではなく、構造的・制度的な問題が複合的に絡んでいます。

---

## 2. 導入が進まない要因：多面的な分析

### 2-1. 制度・経済的障壁（最大の障壁）

#### 病院の収益構造がIT投資を許さない

日本の病院の**医業利益率は平均1%前後**と極めて低い水準です。これは「診療による収入（診療報酬）」から「人件費・薬剤費・設備費」を引いた残りが、収益のたった1%しかないという意味です。

この数字が示すのは：
- **大きな初期投資が出来ない**：数千万円規模のシステム導入は即座に経営危機につながる
- **失敗が許されない**：投資がムダになると取り返しがつかない
- 日本の病院の**74.6%が医業赤字**（本業の診療で赤字）の状態

#### 「AIを入れても収益が増えない」ジレンマ

医療サービスの価格は**診療報酬（公定価格）**で固定されています。

> 例えば、AIを使って診断精度が上がっても、保険点数（収益）は変わりません。
> AIを入れて生産性が2倍になっても、2倍の診療をする余力も必要性もない病院がほとんどです。

- AI投資のコストを**診療報酬に上乗せできない**
- 2024年度改定で「画像診断管理加算3・4」が新設されAI画像診断への加算が一部可能になったが、**対象は大規模病院に限定**
- 費用対効果の計算が成立しにくい構造になっている

#### 診療報酬への収載までの「ニワトリと卵」問題

AIを診療報酬の加算対象にするには実績が必要 → 実績を積むには先に自費で投資しなければならない → でも投資コストを回収できる保証がない、という悪循環があります。

---

### 2-2. 技術的・システム的障壁（ベンダーロックイン）

#### 電子カルテ市場の寡占構造

日本の病院の電子カルテ市場は、**富士通・CSI・NEC・日立ソフトウェアサービスなどの大手が市場の約70%を占める**寡占状態です。

これが問題な理由：
- 各ベンダーが独自のデータ形式を使用しており、**異なるシステム間でのデータ連携が困難**
- 電子カルテの更新サイクルは**5〜6年ごと**で、数億円規模の費用がかかる
- 一度導入すると乗り換えコストが異常に高い（「一種の鎖に近い」状態）

#### Amazon Bedrock/Azure OpenAI との連携における5重の壁

電子カルテとAIを繋ごうとすると、具体的に以下の壁があります：

| 壁 | 内容 |
|---|---|
| **① APIの不在** | 古い電子カルテはREST APIすら持っていない |
| **② セキュリティ要件** | 患者データをAIベンダーに送ることで生じる法的責任 |
| **③ ベンダーの抵抗感** | 電子カルテベンダーが自社AI以外の接続仕様を公開しない |
| **④ AIの法的グレーゾーン** | AI出力が誤診につながった場合の責任の所在不明 |
| **⑤ クラウドへの根強い抵抗** | 「患者データをクラウドに送ること」への心理的抵抗 |

#### データ標準化の遅れ

- 病院間での電子的なデータ連携はわずか**0.4%**
- 残りは依然としてFAXと紙（2024年時点）
- FHIR（国際標準の医療データ形式）の導入は、2025年度から「電子カルテ情報共有サービス」として始まったばかりで、全体普及には**10年単位の時間**がかかる見込み

### 2-3. 規制・法的障壁

#### 厚生労働省ガイドラインの影響

2023年5月に「医療情報システムの安全管理に関するガイドライン 第6.0版」が公表されました。

**内容自体はクラウド利用を認める方向**（それまでのグレーゾーンを解消）。ただし：
- クラウド利用には「医療機関がクラウド事業者を監督する義務」が発生
- サイバーセキュリティ対策チェックリストの全項目対応が義務化（2024年度末まで）
- **逆説的問題**：ガイドライン対応のためのセキュリティ投資が、中小病院のDX化をさらに遅らせる

#### 薬機法によるAI医療ソフトウェア規制（SaMD）

診断や治療の補助を目的とするAIソフトウェアは、**「医療機器プログラム（SaMD: Software as a Medical Device）」として薬機法の承認が必要**です。

現状：
- PMDA（独立行政法人医薬品医療機器総合機構）による審査・承認が必要
- 2025年時点で承認済みのAI医療機器は**わずか50件程度**
- 最大の問題：**「承認後にモデルを更新できない」** ← AIの本質的な強みである継続的な学習・改善が規制と衝突する
- 2024年7月にPMDA「改良型大臣確認等（3段階のうち2段階で書面対応）」が整備されたが、根本的な解決には至っていない

#### 患者データの取り扱い

- 患者情報は「要配慮個人情報」として厳格な取り扱いが必要
- AI学習用にデータを使用するには**患者の同意取得またはIRB（倫理審査委員会）審査**が必要
- クラウド事業者への委託は認められるが、**委託元の病院に監督義務**が残る
- 音声データには患者の声が含まれるため「生体情報」として特に慎重な扱いが求められる

### 2-4. 人材・組織文化的障壁

#### IT人材の圧倒的な不足

- 「必要なスキルを持った人材がいない」 → ヘルスケア業界でAI普及の最大の課題（PwC調査）
- **医師の約4人に1人**しかAIを業務利用した経験がない
- **看護師の7.5%**しかAIを業務利用した経験がない（Indeed調査）
- 中小規模の病院には**IT担当者すら専任でいない**ところが多い

#### 意思決定プロセスの複雑さ

病院のIT導入には複数のステークホルダーの合意が必要です：

```
院長 → 副院長（診療系） → 事務長 → IT担当 → 各科の部長 → 診療情報管理士
```

これらが合議制で決定するため、意思決定に**1〜2年以上**かかることが珍しくありません。最終決定者（院長）は医師であることが多く、IT的な観点より「現場で使いやすいか」「実績はあるか」「安全か」が優先されます。

#### 「現状で運営できている」という現場の意識

特に地方の中小病院では「今のやり方で何十年も問題なかった」という意識が根強く、変化への動機が生まれにくい構造があります。

---

### 2-5. セキュリティ障壁

ランサムウェア攻撃の被害が急増しています：

- 医療機関を対象にしたランサムウェア被害率：2021年34% → **2024年67%** （Sophos調査）
- 岡山県精神科医療センター（2024年5月）など高プロファイルな被害事例が相次ぐ
- 被害に遭うと電子カルテが使えなくなり、**紙のカルテに戻す**という事態が発生

この状況が、逆説的に「クラウド・AI化への心理的抵抗」を強めています。「オンプレミスの方が安全だ」という（必ずしも正確ではない）認識が広まっています。

## 3. 議事録・音声AIが普及しない具体的理由

「AWSのAmazon Transcribeを日本リージョンで使えば、すぐに議事録が作れるのに」という感覚は正しいです。技術的には確かにすぐできます。ではなぜ普及しないのか。

### 理由① 音声データが「患者情報」を含む可能性

病院内の会議・カンファレンスの音声には：
- 患者の氏名・病名・症例情報が含まれることが多い
- これは**「要配慮個人情報」**であり、クラウドに送信すること自体がリスクになる
- 「AWS東京リージョンだから安全」という理解では不十分で、**データ処理委託の契約・管理体制**が必要

### 理由② 医療用語の認識精度

AWSのAmazon TranscribeやAzure Speech Servicesは汎用的な音声認識です：
- **医療専門用語（薬品名・術式名・解剖学用語）の認識精度が低い**
- 「アミオダロン」「冠動脈バイパス術」「縫合不全」などが正確に書き起こされない
- 誤った医療記録が作られるリスクを医師が恐れる

### 理由③ 責任の所在

AI生成の議事録に誤りがあった場合：
- それを確認・訂正した人が責任を負うのか
- そのまま記録として残った場合の法的責任は誰か

という問題に明確なルールがなく、現場が導入をためらいます。

### 理由④ AWSの医療特化サービスが日本語に対応していない（盲点）

「AWSの日本リージョンで音声認識を使えばいい」という感覚は半分正解ですが、重要な落とし穴があります。

> **Amazon Transcribe Medical（医療特化の音声認識）は、現時点で英語のみ対応。**
> 日本語医療現場での利用には「汎用のAmazon Transcribe（日本語対応）＋カスタム辞書」という迂回運用が必要になります。

つまり、「AWSで即日できる」は技術的に正しいが、**医療用語精度の担保という点で追加の整備コストが発生する**という問題があります。

### 理由⑤ 既存ワークフローとの摩擦

「会議のたびにマイクを設置して録音する」という新しいステップを加えること自体への抵抗感があります。病院スタッフはすでに非常に多忙であり、「新しいことを覚えて運用するコスト」が高く感じられます。

また、**「発言が記録に残ること」への心理的抵抗**も見逃せません。カンファレンスでの発言が「証拠として残る」ことを医師・看護師が嫌がるケースがあります。

## 4. 海外との比較：なぜ日本だけ遅れているのか

### 米国の状況

- **大規模病院（400床以上）でのAI活用率：90〜96%**（2025年時点）
- 電子カルテ最大手「Epic」とMicrosoftが連携し、AIを電子カルテに直接組み込む
- 「Ambient Listening（アンビエント聴取）」という仕組みで、医師が患者と話しながらAIが自動でカルテを生成 → **カルテ作成時間を最大50%削減**
- これが機能する理由：EpicというデファクトスタンダードのEHRに、MicrosoftのAIが統合済みのため、病院が個別に統合作業をする必要がない

### シンガポールの状況

- 2011年から国主導で**全国電子健康記録（NEHR）**を構築
- 「One Patient, One Health Record（1患者1記録）」の原則で、国中どこの病院でも同じデータを参照可能
- AIはこの統合データベースで学習できるため精度が高い

### 韓国の状況

- 漢陽大学病院が院内LLMを電子カルテに組み込む「Y-KNOTプロジェクト」を実施
- 手術記録の要約精度：**92.7% → 98.0%** に向上
- Naver・Kakaoなど国内IT大手が医療分野に積極参入し、スピードが速い

### 日本の構造的な3つの遅れ

| 問題 | 内容 |
|------|------|
| **診療報酬制度によるIT投資の阻害** | AI活用による価値向上を収益に直結させる仕組みがない |
| **ベンダーロックインと標準化の失敗** | 各社バラバラのシステムが30年かけて積み上がり、AI学習データの確保が根本的に妨げられている |
| **中小病院の経営的厳しさ** | 200床以下の中小病院は電子カルテ普及率がようやく59%に達した段階で、AIどころかクラウド化の基盤すら整っていない |

なお、電子処方箋の普及率は**薬局86.5%に対して病院はわずか17.3%**（2025年10月時点）。「2025年3月までにほぼ全病院で普及」という目標は達成されず、2026年再度計画が練り直されています。

### 逆転現象：日本が世界トップクラスの分野もある

内視鏡（胃カメラ・大腸カメラ）によるポリープ検出AIでは、**日本の研究機関・企業が世界最高水準の精度**を達成している。これは日本が世界有数の内視鏡検診件数を持ち、良質な学習データが確保できたためです。「日本は全般的にAIが遅れている」のではなく、「データが集まる分野では先行できる」という構造的な特徴があります。

米国では Ambient Documentation（会話を聞いてAIが自動でカルテを生成）による医師の燃え尽き症候群の感覚が**70%減少**したという報告もあり、この機能の普及が日米格差をさらに広げる可能性があります。

## 5. 内製化（自前開発）は進むのか？

### 先進的な内製化事例（実際にやっている病院）

| 病院 | 取り組み内容 | 特徴 |
|------|------------|------|
| **HITO病院**（愛媛県、228床） | Azure OpenAI + 電子カルテ連携で症状詳記（診療報酬請求書類）自動生成、Microsoft Fabricで人員配置ダッシュボード、AI多言語翻訳で海外スタッフが単独夜勤対応 | 全職員にiPhoneを配布しCopilotを全員利用。脳神経外科部長がCTOを兼任するDX体制が成功の鍵 |
| **NTT東日本関東病院** | Microsoft 365 E5 + Power Apps/Automateで業務フローをSEが内部開発 | 安全管理ガイドライン対応のDX推進モデルとして評価 |
| **済生会熊本病院**（400床） | Power Appsで薬品管理システムを内製 | ローコード活用で短期間・低コスト開発を実証 |
| **雄勝中央病院**（秋田県、離島） | FileMaker活用で200床以下でも内製化可能なことを実証 | 小規模病院でも内製化の可能性あり |
| **那須赤十字病院** | リコー製700億パラメータLLMをオンプレミス設置 | データ院外流出ゼロ。退院サマリー・薬品情報を自動生成。2024年に実装 |

### 内製化が進む理由

1. **2024年医師の働き方改革（残業上限規制）の施行**：2024年4月から医師の時間外労働に上限が適用され、書類作成・事務作業の効率化が「待ったなし」の課題に。外部委託では対応が遅すぎるため、病院自身がアプリを作る動機が急増
2. **クラウドの民主化**：AWS Bedrock・Azure OpenAI APIは誰でも使える
3. **ローコード/ノーコードの普及**：Power Apps・Notionなどを使えば、エンジニアなしでも機能を追加できる。「市民開発」として医師・看護師・事務員が自らアプリを作る事例も出てきた
4. **外部ベンダーへの不満の蓄積**：「自分たちに合わないシステムを押し付けられてきた」という意識
5. **補助金の整備**：東京都をはじめ自治体がAI導入補助金を整備しつつある

### 内製化の限界

一方で、すべての病院が内製化できるわけではありません：
- **IT人材の採用競争が激化**：2025〜2026年には全国22万人規模のIT人材不足が予測される
- 医療SE（システムエンジニア）の平均年収：**510〜542万円**（IT業界平均より低め）
- DX推進リーダー（CTO相当）なら**600〜800万円**が必要で、中小病院には難しい水準
- 大規模病院（500床以上）や国立・大学附属病院でないと、内製化を担えるチームを持てない

### 現実的な展望

> 完全内製化は難しいが、**「外部プラットフォーム（クラウド）＋内部カスタマイズ」** というハイブリッドモデルが現実解として普及していくと見られます。

具体的には：
- Microsoft 365（Teams・SharePoint・Power Automate）を基盤にして業務フロー自動化
- AWS Bedrockを使ったAIチャット基盤を「外部ベンダーに依存せず」自院で管理
- 機能は小さく始めて（スモールスタート）、段階的に追加していく

## 6. 病院がAIプラットフォームを構築する場合のコスト概算

### ① API利用コスト（月額）

2025年時点のAPIモデル別の単価（目安）：

| AIモデル | 入力トークン単価 | 出力トークン単価 |
|---------|------------|------------|
| Claude 3 Haiku（AWS Bedrock） | $0.25/100万トークン | $1.25/100万トークン |
| Claude Sonnet 4.5（AWS Bedrock） | $3.00/100万トークン | $15.00/100万トークン |
| GPT-4o mini（Azure OpenAI） | $0.15/100万トークン | $0.60/100万トークン |
| GPT-4o（Azure OpenAI） | $2.50/100万トークン | $10.00/100万トークン |

#### 具体例：月50件の外来記録をAIで要約する場合

1件の診療記録を要約するトークン数を1〜2万トークンと仮定：
- Claude Sonnet使用時：1件あたり約**13〜32円**のAPI利用料
- 月50件 × 32円 = 月**1,600円程度**

**API利用料そのものは驚くほど安い**のが現実です。コストの大部分は開発・運用にあります。

### ② クラウドインフラ費用（AWS月額目安）

| 規模 | 想定用途 | 月額目安 |
|------|---------|---------|
| **小規模**（業務AI＋アプリ） | 議事録生成・Q&Aチャット | 5〜15万円/月 |
| **中規模**（外来AI補助） | 診療サマリー・検索・AI補助 | 10〜30万円/月 |
| **大規模**（電子カルテ連携＋DWH） | 全科AI活用・データ分析基盤 | 30〜100万円/月以上 |

### ③ 開発・導入コスト（初期費用）

**プロジェクト規模別の概算：**

| フェーズ | 内容 | 費用目安 |
|--------|------|---------|
| **POC（実証実験）** | 1機能（例：議事録AI）の試作 | 100〜300万円 |
| **MVP開発（本格導入）** | 2〜3機能の基本プラットフォーム | 500〜1,500万円 |
| **フル機能プラットフォーム** | 電子カルテ連携含む複合システム | 3,000万円〜 |

**比較：外部ベンダーへの委託**

外部の医療IT企業が同じものを作ると：
- 議事録AI専用ツール：**1,400〜1,600万円**（6ヶ月）
- 内部チームが開発すると：**900〜1,100万円**（6ヶ月）
- Power Appsローコード開発なら：**200〜400万円**（1件・3ヶ月）

→ 補助金を使えば実質負担額は**100〜200万円台**も可能

### ④ 段階的な開発（アジャイル）での追加コスト

機能を少しずつ追加していく「アジャイル開発」の場合：

- 1スプリント（2週間）あたりの人件費のみ：**20〜40万円**
- 月1回のリリース＝月40〜80万円程度の追加コスト（外部エンジニア委託の場合）
- 内部IT人材が担当できれば：**ほぼゼロの追加費用**で機能拡張が可能

### ⑤ 補助金・助成金の活用

- **東京都AI導入補助金**：最大1,000万円、補助率1/2（実質500万円負担）
- **中小企業デジタル化応援隊事業**（経産省）
- **医療DX推進補助金**（厚労省）：2024年から複数の加算設定が追加

## 7. まとめ：なぜ「簡単なはず」なのに普及しないのか

技術的な難しさではありません。問題の本質は **「制度・経済・組織の三重構造」** にあります。

```
[ 制度的障壁 ]          [ 経済的障壁 ]         [ 組織的障壁 ]
診療報酬制度の硬直性   医業利益率1%前後       意思決定の長さ（1〜2年）
SaMD規制の複雑さ     IT投資回収の困難さ      IT人材の絶対的不足
個人情報法の厳格さ    ベンダーロックイン費用   変化への現場抵抗

              ↓↓↓ 三重構造が絡み合って ↓↓↓

         日本の病院AI導入率：7〜11%（米国の10分の1以下）
```

**「Amazon BedrockのAPIを使えばすぐできるのに」は正しい。** しかし、それを「安全に」「継続的に」「院内に受け入れられる形で」運用する仕組みを整えることが、技術を超えた本当の課題なのです。

### 今後の展望（2026〜2030年）

1. **FHIR標準化の普及**（2025〜2028年）により、電子カルテとAIの連携コストが大幅に下がる可能性
2. **ハイブリッド内製化**（クラウド基盤＋内部カスタマイズ）モデルが大病院から普及
3. **規制の整備**：SaMDの継続的更新を認める仕組みが整えば、診断支援AIが爆発的に普及する可能性
4. **中小病院は当面困難**：IT人材不足と経営的制約から、地域の核となる中核病院への機能集中が加速
5. **放射線科・病理系AIは先行**：診断支援AIのSaMD承認が進んでおり、画像系では先行普及中
