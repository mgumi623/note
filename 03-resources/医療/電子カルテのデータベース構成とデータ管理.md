# 電子カルテのデータベース構成とデータ管理

電子カルテ（EMR: Electronic Medical Record / EHR: Electronic Health Record）は、患者の診療記録をデジタルで管理するシステムです。本ノートでは、電子カルテの「裏側」、つまりデータがどのように保存・保護・バックアップされているかを詳しく解説します。

---

## 1. 電子カルテで使われるデータベース

### 1-1. 日本の主要電子カルテベンダーと市場シェア

日本の病院向け電子カルテ市場は、大手3社で約70%のシェアを占めています。

| ベンダー | 主要製品 | 対象規模 | 推定シェア |
|---------|---------|---------|-----------|
| **富士通Japan** | HOPE LifeMark-HX / HX Cloud | 大中規模病院（300床以上〜） | 約35%（大規模病院でトップ） |
| **NEC** | MegaOakHR | 大中規模病院 | 約15〜20%（227病院で稼働、2021年時点） |
| **ソフトウェア・サービス** | e-カルテ / iChartシリーズ | 中規模病院 | 約15〜20% |
| **ウィーメックス（旧PHC）** | Medicom-HSf / HRf / クラウドカルテ | 診療所〜中規模病院 | 診療所向けで高シェア |
| **エムスリーデジカル** | デジカル | 診療所 | クラウド型で急成長中 |
| **メドレー** | CLINICS | 診療所 | クラウド型で急成長中 |

**補足：市場の変化**
- 大規模病院では従来型（オンプレミス型）が主流だが、クラウド型の浸透が始まっている
- 診療所（クリニック）向け市場では、エムスリーデジカルやメドレーなどのクラウド型が急速にシェアを拡大
- 2024年度の診療報酬改定で、電子カルテ導入がさらに加速すると予想されている

### 1-2. 使用されるデータベース管理システム（DBMS）

電子カルテの内部で使用されているデータベースは、ベンダーや製品によって異なります。

#### Oracle Database

Oracle Database（オラクルデータベース）とは、米国Oracle社が開発した世界最大シェアの商用リレーショナルデータベースです。

- **採用状況**: 大規模病院向け電子カルテで広く使用されている。特に富士通HOPEシリーズやNEC MegaOakなど、ミッションクリティカルな（停止が許されない）基幹システムで採用実績が多い
- **選ばれる理由**: 高い信頼性・可用性（RAC構成による冗長化）、大量データ処理の性能、長年の医療分野での実績
- **特徴的な機能**: TDE（Transparent Data Encryption＝透過的データ暗号化。アプリケーション側を変更せずにデータベースレベルで暗号化する機能）、Data Guard（災害対策用のデータ複製機能）
- **ライセンスコスト**: 高額なため、大規模病院でないと採用しにくい

#### Microsoft SQL Server

SQL Server（エスキューエルサーバー）とは、米国Microsoft社が開発した商用データベースで、Windows環境との親和性が高いのが特徴です。

- **採用状況**: 中規模病院向け電子カルテや医事会計システムで使用されている
- **選ばれる理由**: Windows Serverとの統合性、比較的手頃なライセンスコスト、管理ツール（SQL Server Management Studio）の使いやすさ
- **特徴的な機能**: Always On可用性グループ（自動フェイルオーバー機能）、TDE（透過的データ暗号化）

#### PostgreSQL

PostgreSQL（ポストグレスキューエル）とは、オープンソースのリレーショナルデータベースで、商用利用も無料で可能です。

- **採用状況**: クラウド型電子カルテや新興ベンダーの製品で採用が増加。NECもPostgreSQL関連の技術支援・保守サポートを提供している
- **選ばれる理由**: ライセンス費用が不要、拡張性が高い、HL7やISO EN 13606などの医療データ標準に適したデータ型を定義できる
- **研究実績**: ISO EN 13606（医療情報通信の国際標準規格）に準拠した電子カルテサーバーがPostgreSQLで実装された事例が論文で報告されている
- **注意点**: 商用DBに比べてベンダーサポートが弱い場合があり、ミッションクリティカルな用途では別途サポート契約が必要

#### Caché（キャシェ）/ InterSystems IRIS

Caché（キャシェ）とは、米国InterSystems社が開発した「ポストリレーショナルデータベース」で、従来のリレーショナルDB（表形式）とオブジェクト指向を組み合わせた構造を持ちます。

- **採用状況**: 宮崎大学病院の電子カルテ「Izanami」で使用実績あり。海外では大手EHR（Epic等）で採用
- **特徴**: リレーショナルDBよりも高速に動作することが実証されており、リアルタイム処理が求められる電子カルテに適している
- **補足**: InterSystems社はCachéの後継として「InterSystems IRIS」を提供しており、最新システムではIRISへの移行が進んでいる

### 1-3. SS-MIX2（標準化ストレージ）の仕組み

SS-MIX2（Standardized Structured Medical Information eXchange 2）とは、異なるベンダーの電子カルテ間でデータを共有するための「標準化された保管庫（ストレージ）」のことです。

#### SS-MIX2が必要な理由

日本の電子カルテ市場は多数のベンダーが存在し、各社が独自のデータ形式を使用しています。そのため、A病院の電子カルテのデータをB病院で読み取ることが困難でした。SS-MIX2は、この「データの壁」を解消するために厚生労働省主導で策定されました。

#### SS-MIX2の構造

SS-MIX2は以下の4つの要素で構成されています。

1. **標準化ストレージ**
   - 患者基本情報、検体検査結果、処方オーダ情報などを、国際標準規格「HL7 V2.5」（後述）のデータ形式で保存
   - フォルダ構成は「患者ID → 診療日 → データ種別」の階層で整理
   - つまり、各データが「どの患者の、いつの、何のデータか」がフォルダ名だけで分かる仕組み

2. **拡張ストレージ**
   - 標準化ストレージでカバーしきれない独自データ（各病院固有のデータなど）を格納する領域
   - 標準化ストレージと同じフォルダ構造を持つが、データ形式はベンダーごとに異なる場合がある

3. **トランザクションストレージ**
   - データの更新履歴を時系列で保存する領域
   - 「いつ、何が変更されたか」を追跡できる

4. **インデックスデータベース**
   - リレーショナルデータベース（RDB）で構築された検索用インデックス
   - 複数の患者にまたがる横断的な検索（例：「ある検査値が異常な患者を全て抽出」）を高速に行うための仕組み

#### SS-MIX2のデータ形式

SS-MIX2では、データを「HL7 V2.5」（ISO/HL7 27931:2009）という国際標準メッセージ形式で記述します。これは医療情報を構造化されたテキストメッセージとして表現する規格で、世界中の医療システムで広く使用されています。

### 1-4. HL7 FHIR（医療データの次世代標準規格）

HL7 FHIR（Fast Healthcare Interoperability Resources、読み方：「ファイア」）とは、医療情報を異なるシステム間で交換するための最新の国際標準規格です。

#### HL7 FHIRとは何か

従来のHL7 V2.5が「テキストメッセージ」ベースだったのに対し、FHIRは**Web技術（REST API、JSON/XML）**をベースにしています。つまり、現代のWebサービスやスマートフォンアプリと同じ技術で医療データをやり取りできるため、開発の敷居が大幅に下がりました。

#### FHIRの基本概念「リソース」

FHIRでは、医療データを「リソース」と呼ばれる単位で管理します。例えば：
- **Patient**（患者）：氏名、生年月日、性別などの基本情報
- **Observation**（観察・検査結果）：検査値、バイタルサインなど
- **MedicationRequest**（処方）：薬剤名、用量、投与方法
- **Condition**（病名・診断）：傷病名、診断日、重症度

各リソースはURLで一意に識別でき、リソース間はリンクで関連付けられます。

#### 日本での導入状況（2025〜2026年）

- **電子カルテ情報共有サービス**: 2025年4月より順次運用開始予定。医療機関間で患者の診療情報を電子的に共有するサービスで、データ形式にHL7 FHIRを採用
- **共有対象データ**: 3つの文書（診療情報提供書、退院サマリー、健診報告書）と6つの情報（傷病名、アレルギー、感染症、薬剤禁忌、検査、薬剤情報）
- **各医療機関の対応**: 自院の電子カルテのデータをFHIR形式に変換する仕組みの実装が必要
- **実装ガイド（IG: Implementation Guide）**: FHIRでは「プロファイル」機能でデータルールを定義し、これを集約したIG（実装ガイド）がWebコンテンツとして公開されている

## 2. 患者データの保存方法

### 2-1. データの種類と保存方式

電子カルテが管理するデータは、その性質によって異なる方法で保存されます。

#### 構造化データ（テキスト・数値データ）

診療記録の中で、定型的なフォーマットで管理できるデータです。

| データの種類 | 具体例 | 保存方法 |
|------------|--------|---------|
| 患者基本情報 | 氏名、生年月日、保険情報 | リレーショナルDB（Oracle、SQL Server等）のテーブルに格納 |
| 検体検査結果 | 血液検査値、尿検査値 | 数値データとしてDBに格納。基準値との比較が可能 |
| 処方情報 | 薬剤名、用量、投与方法 | マスターテーブル（薬剤コード一覧）とリンクして管理 |
| 病名・診断 | ICD-10コード、病名 | 標準病名マスターと紐づけて管理 |
| バイタルサイン | 体温、血圧、脈拍 | 時系列データとしてDBに格納 |

#### 非構造化データ（自由記述・文書）

定型フォーマットに収まらないデータです。

- **SOAP形式のカルテ記載**: 医師が自由文で記述する診療記録。テキストとしてDBに保存（CLOB型など大容量テキスト型を使用）
- **看護記録**: 看護師の観察記録。同様にテキストデータとして保存
- **紹介状・退院サマリー**: 文書テンプレートに基づいて作成されたドキュメント

#### 医用画像データ（DICOM形式）

医用画像（CT、MRI、レントゲン等）は「DICOM」（ダイコム: Digital Imaging and Communications in Medicine）という専用規格で管理されます。

**DICOMとは何か**
DICOMとは、医用画像の撮影・保存・通信に関する国際標準規格です。画像データ本体だけでなく、患者ID・撮影日時・撮影条件などの「メタデータ（付属情報）」も一体化して管理できるのが特徴です。

**DICOMデータの特徴**
- 1回のCT検査で数百枚〜数千枚の画像が生成される
- 1患者あたりのデータ量は数GB〜数十GBに達することがある
- 画像の解像度は年々向上しており、データ量は増加の一途

### 2-2. PACS（医用画像管理システム）との連携

PACS（パクス: Picture Archiving and Communication System）とは、DICOMで保存した医用画像を一元管理・配信するシステムです。

#### PACSの構成要素

PACSは以下の要素で構成されています。

1. **アプリケーションサーバ**: DICOM画像データの受信・圧縮・解凍・送信を行う
2. **画像ストレージ**: 画像データを長期保管するためのストレージ（後述のSAN/NAS）
3. **バックアップストレージ**: 画像データのバックアップを保存
4. **インターフェイスサーバ**: 電子カルテの患者情報やオーダ情報との連携を担当
5. **配信サーバ**: 院内端末で画像を閲覧するための配信を行う

#### 電子カルテとPACSの連携フロー

```
[撮影装置(CT/MRI等)] → [DICOM送信] → [PACSサーバ] ← → [電子カルテ]
                                            ↓
                                    [画像ストレージ]
                                            ↓
                                    [院内端末で閲覧]
```

具体的には、以下のように連携します。

1. CT・MRI等の撮影装置がDICOM形式で画像を生成
2. PACSサーバが画像を受信し、ストレージに保存
3. 電子カルテから「この患者の画像を見たい」とリクエストすると、PACSが該当画像を配信
4. 医師は電子カルテの画面上で画像を閲覧できる

#### PACS導入形態

- **オンプレミス型**: 病院内にサーバ・ストレージを設置して運用。データが院内にあるため高速アクセスが可能だが、設備投資とメンテナンスが必要
- **クラウド型**: インターネット経由で画像を保管・閲覧。他施設とのデータ共有が容易で、院内インフラが不要なため導入コストが安い。ただしネットワーク帯域に依存する

#### 負荷分散の工夫

大規模病院では、登録用と参照用のPACSサーバを分離して負荷を分散させる運用が行われています。画像の書き込み（登録）と読み出し（参照）を別サーバで処理することで、検査中の画像保存と医師による画像閲覧が互いに影響しないようにしています。

### 2-3. データの保存期間（法的要件）

カルテの保存期間は法律で定められており、電子カルテでも紙カルテでも同じ要件が適用されます。

#### 法的な保存義務

| 対象 | 保存期間 | 根拠法令 |
|------|---------|---------|
| **診療録（カルテ）** | 5年間 | 医師法第24条 |
| **診療に関する諸記録**（手術記録、看護記録、検査所見記録等） | 2年間 | 医療法施行規則第20条 |
| **保険診療の記録** | 完結の日から5年間 | 保険医療機関及び保険医療担当規則第9条 |

**重要な注意点**
- 保存期間は「診療日」からではなく「**完結の日**」から起算する。つまり、慢性疾患で通院が続いている場合、通院が終了してから5年間となる
- 実際には、医療訴訟への備えとして**10年以上保存する病院が多い**。民事の損害賠償請求権の消滅時効が最大20年であるため、それに合わせる医療機関もある
- 2023年には厚生労働省に対して「電子カルテの保存義務期間の延長を求める要望書」が提出されている

#### 電子保存の3原則

電子カルテのデータは、厚生労働省のガイドラインにより以下の3原則を満たす必要があります。これを満たさない電子カルテは、保険医療機関として利用できません。

1. **真正性（しんせいせい）**: データが改ざんされていないことを証明できること。具体的には、操作ログ（誰が・いつ・何を変更したか）の記録、電子署名、タイムスタンプなどで担保する
2. **見読性（けんどくせい）**: 保存されたデータを、必要なときにすぐに人間が読める形で表示できること。特定のソフトがないと読めない、といった状態はNG
3. **保存性**: データが保存期間中に消失・破損しないこと。ハードウェアの故障、ソフトウェアのバグ、ウイルスなどからデータを守る措置が必要

### 2-4. ストレージ構成

大規模病院では、膨大な医療データを安全かつ高速に管理するために、専用のストレージ構成を採用しています。

#### SAN（Storage Area Network）

SAN（サン）とは、サーバとストレージ装置を高速な専用ネットワークで接続する方式です。

- **特徴**: 通常のLAN（院内ネットワーク）とは別の専用回線でストレージにアクセスするため、非常に高速かつ安定したデータ読み書きが可能
- **用途**: 電子カルテの本体データベース（Oracle、SQL Server等）の格納先として使用
- **接続方式**: Fibre Channel（FC）という高速通信プロトコルを使用（8Gbps〜32Gbps）
- **コスト**: 専用機器が必要なため高額

#### NAS（Network Attached Storage）

NAS（ナス）とは、通常のネットワーク（LAN）に直接接続するファイルサーバ型のストレージです。

- **特徴**: ファイル単位でのアクセスに適しており、複数のサーバから同時にアクセス可能
- **用途**: PACS画像の保存、文書データの保管、バックアップ先として使用
- **接続方式**: 一般的なイーサネット（1Gbps〜10Gbps）
- **コスト**: SANよりも安価で導入しやすい

#### 一般的な構成パターン

```
[電子カルテDB]  ← → [SAN（高速ストレージ）] ← 高頻度アクセスのデータ
[PACSサーバ]   ← → [NAS（大容量ストレージ）] ← 画像データの長期保存
[バックアップ]  ← → [テープ/クラウド]         ← アーカイブ用
```

大規模病院では、頻繁にアクセスするデータ（直近の診療記録など）はSAN上の高速ストレージに、アクセス頻度の低い過去データはNASやテープに階層的に保存する「HSM（Hierarchical Storage Management＝階層型ストレージ管理）」を採用することがあります。

## 3. データの暗号化

### 3-1. 保存時暗号化（Encryption at Rest）

保存時暗号化とは、ストレージ（ハードディスクやSSD）に保存されているデータを暗号化することです。万が一ストレージが物理的に盗難にあっても、暗号鍵なしではデータを読み取れません。

#### 主な暗号化方式

1. **TDE（Transparent Data Encryption＝透過的データ暗号化）**
   - Oracle Database、SQL Serverが標準機能として提供
   - 「透過的」とは、アプリケーション（電子カルテ本体）を一切変更せずに、データベースレベルで自動的に暗号化・復号が行われるという意味
   - データをディスクに書き込む際に自動的に暗号化され、読み出す際に自動的に復号される
   - 暗号化アルゴリズムは**AES-256**（Advanced Encryption Standard、256ビット鍵長）が推奨される

2. **ボリュームレベル暗号化**
   - ストレージ装置自体が暗号化機能を持つ方式（Self-Encrypting Drive: SED）
   - OSレベルの暗号化（WindowsのBitLocker、LinuxのLUKSなど）
   - ストレージ全体を暗号化するため、データベースに限らず全ファイルが保護される

3. **ファイルレベル暗号化**
   - 個々のファイルを暗号化する方式
   - DICOM画像ファイルなど、データベースに格納されないファイルに対して使用

#### 暗号鍵の管理

暗号化で最も重要なのは「暗号鍵の管理」です。鍵が漏洩すれば暗号化は無意味になります。

- **HSM（Hardware Security Module）**: 暗号鍵を専用のハードウェアデバイスで管理する方式。FIPS 140-2（米国連邦政府の暗号モジュールの認定基準）に準拠したものが推奨される
- **鍵の自動ローテーション**: 定期的に暗号鍵を更新する仕組み。古い鍵で暗号化されたデータは新しい鍵で再暗号化される
- **鍵管理ログの保存**: 鍵に関する操作ログを最低7年間保存することが推奨される（米国HIPAA基準）

### 3-2. 通信時暗号化（Encryption in Transit）

通信時暗号化とは、ネットワーク上を流れるデータを暗号化することです。電子カルテのクライアント端末とサーバ間、あるいは他の医療機関との間のデータ通信を保護します。

#### 主な暗号化プロトコル

- **TLS 1.2 / TLS 1.3**: Webブラウザでの暗号化通信（HTTPS）と同じ仕組み。電子カルテのクライアント-サーバ間通信に使用。TLS 1.2以上が必須で、古いバージョン（SSL、TLS 1.0/1.1）はセキュリティ上の脆弱性があるため使用禁止
- **IPsec VPN**: 拠点間通信（本院と分院の間など）を暗号化するために使用。ネットワーク層で暗号化するため、アプリケーションを意識せずに全通信を保護
- **DICOM TLS**: PACS間の医用画像通信を暗号化するためのプロトコル。DICOM規格にTLSが組み込まれている

### 3-3. 暗号化の実施状況（日本の現実）

#### 実態としての課題

日本の医療機関における暗号化の実施状況は、残念ながら十分とは言えません。

- **保存時暗号化**: 大規模病院（大学病院、国立病院機構など）では導入が進んでいるが、中小規模の病院やクリニックでは未実施のケースが多い
- **通信時暗号化**: 院内ネットワーク内の通信は暗号化されていないケースが散見される。特に古い電子カルテシステムでは、平文（暗号化されていない状態）で通信しているものもある
- **可搬媒体の暗号化**: USBメモリやCD-Rなどの可搬媒体の暗号化・持ち出し禁止の徹底が「いまだ道半ば」の状態にある

#### ランサムウェア被害の実態

暗号化対策の不備が如実に表れたのが、相次ぐランサムウェア被害です。

- **2021年10月**: 徳島県つるぎ町立半田病院がランサムウェア「LockBit」に感染。電子カルテが使用不能になり、約2か月間通常診療が不可能に
- **2022年10月**: 大阪急性期・総合医療センターがランサムウェア攻撃を受け、電子カルテシステムに障害が発生。約2か月間の診療制限
- **2024年**: 岡山県精神科医療センターなど、引き続き医療機関への攻撃が継続

**なぜ医療機関が狙われるのか**
- 患者の生命に直結するため、身代金を支払う可能性が高いと犯罪者に認識されている
- 医療業界の約57%が過去3年間にランサムウェアに感染し、うち約25%は業務を完全に停止
- セキュリティ対策の予算・人材が不足している医療機関が多い

#### 3省2ガイドラインの要請

厚生労働省「医療情報システムの安全管理に関するガイドライン（第6.0版、2023年5月改定）」では、以下を要求しています。

- 保存データの暗号化
- 通信経路の暗号化（TLS 1.2以上）
- アクセスログの記録・保存
- 不正ソフトウェア対策

ただし、ガイドラインはあくまで「指針」であり、法的強制力が弱いため、対応状況は各医療機関に依存しているのが現状です。

## 4. バックアップ体制

### 4-1. バックアップ方式の種類

電子カルテのバックアップは、データ量と復旧速度のバランスを考慮して、複数の方式を組み合わせるのが一般的です。

| バックアップ方式 | 仕組み | メリット | デメリット |
|----------------|--------|---------|-----------|
| **フルバックアップ** | 全データを丸ごとコピー | 復旧が簡単・高速 | データ量が大きく、時間がかかる |
| **差分バックアップ** | 前回のフルバックアップからの変更分をコピー | フルよりデータ量が少ない | 日が経つにつれデータ量が増加 |
| **増分バックアップ** | 前回のバックアップ（フル・増分問わず）からの変更分のみコピー | 最もデータ量が少なく高速 | 復旧時に全ての増分を順番に適用する必要があり時間がかかる |

#### 一般的な運用パターン

多くの医療機関では以下のような組み合わせを採用しています。

- **日次**: 増分バックアップ（毎日の変更分を保存）
- **週次**: 差分バックアップまたはフルバックアップ
- **月次**: フルバックアップ
- **データベースのトランザクションログ**: リアルタイムまたは数分間隔で取得

### 4-2. バックアップの保管場所

#### 3-2-1ルール

バックアップの保管には「**3-2-1ルール**」が世界標準とされています。

- **3**: データのコピーを**3つ**持つ（本番データ + バックアップ2つ）
- **2**: **2種類**の異なるメディア（媒体）に保存する（例：ディスク + テープ、ディスク + クラウド）
- **1**: **1つ**はオフサイト（遠隔地）に保管する

ただし、HIPAA Journal（米国医療情報プライバシーに関する専門メディア）の調査によると、この3-2-1ルールを遵守している組織は全体の**わずか5分の1（約20%）**にとどまっています。

#### 保管場所の選択肢

| 保管場所 | 特徴 | 適したケース |
|---------|------|-------------|
| **オンサイト（院内）** | サーバ室内のバックアップ用ストレージ。復旧が最速だが、災害時に本番と共に被災するリスク | 日常的な障害復旧用 |
| **オフサイト（遠隔地）** | 別の建物・地域にあるデータセンターに保管。災害対策として有効 | BCP（事業継続計画）対策 |
| **クラウド** | AWS S3、Azure Blob Storageなど。容量の制限がなく、地理的な冗長性も確保可能 | コスト効率の良い長期保存 |
| **テープ（LTO）** | 磁気テープに保存する方式。ネットワークから物理的に隔離されるためランサムウェア耐性が高い | オフラインバックアップ |

### 4-3. ランサムウェア対策としてのバックアップ

#### なぜオフラインバックアップが重要か

最近のランサムウェアは、本番システムだけでなく**ネットワーク上のバックアップデータも暗号化する**という進化を遂げています。つまり、バックアップがオンライン（ネットワーク接続された状態）にある場合、バックアップごと使えなくなるリスクがあります。

#### 効果的な対策

1. **エアギャップ（Air Gap）バックアップ**
   - ネットワークから物理的に切り離された状態でバックアップを保管する方式
   - 具体的にはLTOテープにバックアップを取得し、テープを耐火金庫や別拠点に保管
   - バックアップをオフラインで保管していた半田病院のようなケースでは、感染発覚から数日でシステムを復旧できた事例がある

2. **イミュータブル（Immutable＝変更不可能な）バックアップ**
   - 一度書き込んだデータを一定期間変更・削除できないようにする機能
   - AWS S3 Object Lock、Azure Immutable Blob Storageなどのクラウドサービスで利用可能
   - ランサムウェアがバックアップにアクセスしても、暗号化や削除ができない

3. **ネットワーク分離**
   - 電子カルテ（EHR）、PACS、検査系、事務系（医事会計・人事）のネットワークを分離
   - 双方向通信はプロキシサーバを経由して最小化する
   - 1つのシステムが感染しても、他のシステムへの被害拡大を防止

#### 厚労省ガイドラインの対応

厚生労働省の改定ガイドラインでは、ランサムウェアを想定した対策として「電子カルテなどのバックアップデータはネットワークから切り離し『独立保管』する」ことが明記されています。

### 4-4. RPO（目標復旧時点）とRTO（目標復旧時間）

RPOとRTOは、災害やシステム障害からの復旧計画を策定する際の2つの重要な指標です。

#### RPO（Recovery Point Objective＝目標復旧時点）

**RPOとは何か**: 「どの時点のデータまで復旧できればよいか」を示す指標。言い換えれば「許容できるデータ損失量」を時間で表したものです。

- RPOが「0」: データ損失を一切許容しない。リアルタイムでのデータ複製が必要
- RPOが「1時間」: 最大1時間分のデータ損失を許容する。1時間ごとにバックアップを取得
- RPOが「24時間」: 最大1日分のデータ損失を許容する。日次バックアップで対応

**電子カルテの場合**: 患者の診療データは極めて重要であるため、RPOは可能な限り短く設定する必要があります。大規模病院では「リアルタイム〜数分」、中規模病院でも「1時間以内」が推奨されます。

#### RTO（Recovery Time Objective＝目標復旧時間）

**RTOとは何か**: 「システム停止からどのくらいの時間で復旧しなければならないか」を示す指標。

- RTOが「0」: ダウンタイム（停止時間）を一切許容しない。冗長構成（Active-Active構成など）が必要
- RTOが「4時間」: 4時間以内にシステムを復旧させる
- RTOが「24時間」: 1日以内に復旧させる

**電子カルテの場合**: 診療が停止すると患者の生命に関わるため、RTOは「数時間以内」が求められます。救急医療を担う病院ではさらに短いRTOが必要です。

#### 推奨される運用

厚生労働省のガイドラインでは、年2回の「実地リストア演習」（実際にバックアップからデータを復元する訓練）を行い、RPO/RTOが計画通りに達成できることを確認することが推奨されています。

## 5. クラウド型電子カルテの台頭

### 5-1. クラウド型とオンプレミス型の違い

| 項目 | オンプレミス型 | クラウド型 |
|------|--------------|-----------|
| **データ保管場所** | 病院内のサーバ室 | AWS、Azure等のデータセンター |
| **初期投資** | 高額（サーバ、ストレージ、ネットワーク機器の購入） | 低額（月額課金制） |
| **運用保守** | 院内のIT担当者が対応 | クラウド事業者が基盤を管理 |
| **システム更新** | 大掛かりな作業が必要（5〜7年ごとのリプレース） | 自動的にアップデートされる |
| **BCP対策** | 病院が独自に災害対策を構築 | クラウド事業者の地理的冗長性を利用可能 |
| **カスタマイズ性** | 高い（自由に設計可能） | 制限がある（マルチテナント方式のため） |

### 5-2. AWS・Azure上の電子カルテ

#### AWS（Amazon Web Services）上の電子カルテ

- **富士通**: 「HOPE LifeMark-HX Cloud」をAWS上で提供
- **NECの対応**: 「医療情報システム向けAWS利用リファレンス」を公開し、3省2ガイドラインへの対応方法を明文化
- **AWSの医療対応**: HIPAA準拠の環境を提供。S3（ストレージ）、RDS（データベース）、KMS（暗号鍵管理）など、医療データ管理に必要なサービスが整っている

#### Microsoft Azure上の電子カルテ

- **Microsoftの姿勢**: 「クラウドサービスにおいてデータの所有者はお客様であり、マイクロソフトがデータを閲覧・活用することはない」と明確に規定
- **3省2ガイドライン対応**: 「医療機関向けクラウドサービス対応セキュリティリファレンス」を公開。Azure、Office 365、Dynamics 365の対応状況が明文化されている点はAWSとの差別化要因
- **標準型電子カルテ**: 厚労省が推進する標準型電子カルテのα版開発をFIXER社が担当しており、Microsoft Azureベースで開発が進められている

### 5-3. クラウド型のメリット

1. **BCP対策の強化**: データが複数のデータセンターに冗長保管されるため、災害時でもデータ消失のリスクが低い。また、IT担当者の感染症等による業務停止リスクも軽減できる
2. **初期投資・運用コストの低減**: サーバ購入が不要で、月額課金制のため計画的な費用管理が可能
3. **調達期間の短縮**: サーバの調達・設置が不要なため、システム導入までの期間を大幅に短縮できる
4. **セキュリティの向上**: AWS、Azureなどの大手クラウドは、個々の病院よりもはるかに高度なセキュリティ基盤を持っている（24時間監視、自動パッチ適用など）
5. **小規模医療機関への普及促進**: IT専任担当者がいない小規模クリニックでも、運用保守の負担が少なく導入しやすい

### 5-4. クラウド型のデメリット・課題

1. **ネットワーク依存**: インターネット回線が停止すると電子カルテにアクセスできなくなる。冗長回線やローカルキャッシュ（院内に一時データを保持する仕組み）の整備が必要
2. **レイテンシ（遅延）**: オンプレミス型に比べて応答速度が遅くなる場合がある。特に画像データの閲覧は帯域の影響を受けやすい
3. **カスタマイズの制限**: マルチテナント方式（複数の医療機関が同じシステム基盤を共有する方式）のため、個別のカスタマイズに制約がある
4. **データの所在**: 患者データが海外のデータセンターに保管される可能性があり、データ主権の観点から懸念がある（ただしAWS、Azureとも日本国内リージョンを提供）
5. **ベンダーロックイン**: 特定のクラウド事業者に依存すると、将来的な移行が困難になるリスク

### 5-5. 3省2ガイドラインとの関係

#### 3省2ガイドラインとは何か

3省2ガイドラインとは、厚生労働省・経済産業省・総務省が制定した、医療情報システムに関する2つのガイドラインの総称です。

1. **厚生労働省**: 「医療情報システムの安全管理に関するガイドライン」（第6.0版、2023年5月改定） → 医療機関向け
2. **経済産業省・総務省**: 「医療情報を取り扱う情報システム・サービスの提供事業者における安全管理ガイドライン」（第2.0版、2025年3月改定） → ベンダー・クラウド事業者向け

#### クラウド型に関する主な要件

- データの保管場所を日本国内に限定する規定（原則として国内データセンターを使用）
- アクセスログの記録・保存
- 暗号化（保存時・通信時）の実施
- バックアップ体制の整備
- 第三者監査の受入れ

#### 3省3ガイドラインへの移行

なお、ガイドラインの呼称について補足すると、2023年以降は経済産業省・総務省の2つのガイドラインが統合されたため「3省2ガイドライン」と呼ばれますが、統合前は「3省3ガイドライン」と呼ばれていました。文献によって呼称が異なる場合がありますが、2025年時点では「3省2ガイドライン」が正式な呼称です。

### 5-6. 標準型電子カルテの動向（2025〜2026年）

厚生労働省は、電子カルテの普及率向上と標準化を目的として「**標準型電子カルテ**」の開発を推進しています。

#### 主な仕様

- **SaaS型クラウド**: ガバメントクラウド上でマルチテナント方式で提供。1つのシステムを複数の医療機関が共同利用することでコスト低減を図る
- **HL7 FHIR対応**: 電子カルテ情報共有サービスとの連携が標準搭載
- **標準API搭載**: 他のシステムとの連携を容易にするためのAPIを標準装備
- **データの互換性**: ベンダーを乗り換える際にデータを引き継げる互換性を確保

#### 開発スケジュール

| 時期 | 内容 |
|------|------|
| 2024年度 | FIXER社がα版システムの開発に着手（無床診療所向け最小構成） |
| 2025年度 | α版の試験運用開始 |
| 2026年度中 | 完成を目指す |
| 2026年夏まで | 具体的な普及計画の策定 |
| 2030年まで | 希望する病院が導入できる環境整備 |
