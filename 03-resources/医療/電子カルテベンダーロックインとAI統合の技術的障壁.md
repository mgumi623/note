# 電子カルテ・ベンダーロックインとAI統合の技術的障壁（Web調査資料）

## 1. 日本の電子カルテ市場のベンダー構造

### 病院向け（オンプレミス型）の市場構造

日本の大規模病院向け電子カルテ（HIS：Hospital Information System）市場は、
いくつかの大手ベンダーによって支配されており、上位数社で市場シェアの約70%を占めている。

主要ベンダーとシェア：
- **富士通**：大規模病院向けでトップシェア（約3割）。「HOPE EGMAIN-GX」「FUJITSU Hospital Information System」を展開
- **CSI（シーエスアイ）**：富士通に次ぐシェアを持つ中大規模病院向けベンダー
- **NEC（NECソリューションイノベータ）**：病院・診療所向け双方に対応。「MegaOak」シリーズ
- **ソフトウェア・サービス（SSI）**：中規模病院向けに強み。「MEDIBASE」
- **日立製作所**：大規模病院向けHIS「HISTORA」などを展開

この構造が「寡占」かどうかの解釈について注意が必要で、電子カルテの技術的な参入障壁自体は
それほど高くないとされている。しかし、**病院側の乗り換えコスト**（データ移行、スタッフ再教育、
システムカスタマイズの喪失）が非常に大きいため、実質的な寡占状態が維持されている。

### クリニック・診療所向け（クラウド型）の市場構造

クリニック向けはクラウド型が急速に普及し、市場の半数程度に達している。
- **エムスリーデジカル（m3）**：クラウド型でトップシェア
- **CLINICS（メドレー）**：急速に伸長中のクラウド型
- **Medicom（ウィーメックス、旧PHC）**：旧パナソニック系。クリニック向けで強い存在感
- **ユヤマ**：調剤系と連携した電子カルテ

### 更新サイクルとコスト

電子カルテシステムの耐用年数は一般的に5〜6年とされており、オンプレミス型では
更新のたびに初回導入と同等のコストが発生する。

費用の目安：
- 大規模病院（200床以上）：初期導入・更新費用が**数千万円〜億単位**
- 中規模病院（100〜200床）：数千万円規模
- クリニック・診療所：300〜500万円程度（オンプレミス型）、または20〜150万円（クラウド型）

更新費用が巨額であることが、ベンダーを変更しない大きな理由のひとつとなっている。

## 2. レガシーシステムとの互換性問題

### 「バラバラな仕様」という構造的問題

日本の電子カルテ最大の問題のひとつは、**ベンダーごとにデータ形式が異なる**ことである。
同じ「患者の検査値」であっても、富士通の電子カルテとNECの電子カルテでは
保存形式・出力形式が根本的に異なる。このため：

1. **病院間での患者データ共有が困難**
   - 患者が転院すると、診療情報が紙の紹介状になることが多い
   - データを電子的に受け渡すには、両院が同一ベンダーのシステムを使っているか、
     特別な変換処理が必要

2. **院内システム間の連携コストが高い**
   - 電子カルテと放射線システム（RIS）、検査システム（LIS）、薬剤システム（PIS）を
     つなぐには、ベンダーごとに個別のインターフェース開発が必要
   - こうした院内の「部門システム」の接続数は大病院で数十〜百件以上にのぼる

3. **病院ごとの独自カスタマイズの蓄積**
   - 電子カルテは病院の業務フローに合わせて大量にカスタマイズされる
   - 10年以上使い続けると、そのカスタマイズが複雑に絡み合い、
     「どこを変えると何が壊れるかわからない」状態になる
   - これをベンダーが「保守のためにはウチのシステムを使い続けるしかない」として
     交渉力を持つ根拠になる

### HL7 FHIR標準化への政府の動き

こうした問題への対応として、日本政府は医療DX令和ビジョン2030の一環として
**HL7 FHIRへの標準化**を推進している。

HL7 FHIRとは：
- HL7（Health Level 7）国際規格の最新版（FHIR = Fast Healthcare Interoperability Resources）
- 医療データをWeb技術（REST API、JSON、XML）で交換するための国際標準規格
- 「患者の検査値はこういうデータ形式で表現する」という共通ルールを定めたもの

現状と課題：
- 2025年度中に「電子カルテ情報共有サービス」の運用開始が目標とされている
- 各医療機関は自院システムをHL7 FHIR形式に対応させる改修が必要
- 政府は改修費用の補助金を提供（200床以上の病院で最大657.9万円、補助率1/2）
- しかし長年積み上げたカスタマイズの全てをFHIR形式に変換することは困難であり、
  移行には10年単位の時間がかかるとみられている

### 順天堂医院の事例：ベンダー依存を脱する大改革

順天堂医院（東京大学医学部附属のレベルの大規模大学病院）は、
2023年1月に大規模なIT基盤刷新を断行した。

問題の状況：
- 物理サーバーが**約260台**に膨らみ、管理が限界に
- 診療画像、薬剤管理、医療事務など各システムがバラバラのベンダーによる「サイロ状態」
- データを一元的に管理・分析することが困難で、DX推進の妨げになっていた

対応策：
- Dell Technologies製「VxRail」を基盤とした**統合仮想化基盤**を構築
- 電子カルテを**富士通から日本IBMに変更**（大規模な乗り換えを実施）
- 臨床系・事務系を含めたほぼ全ての医療情報システムを仮想化基盤に移行
- 「統合ビューア」機能により、将来的にどのベンダーの電子カルテが入っても
  全データを一元管理できる構造に

この事例は例外的なほど大規模な刷新であり、大学病院クラスの資金力と決断力があって
初めて実現できたものである。多くの地域の中小病院にはこうした刷新は困難。

## 3. 電子カルテとAIツールの連携における技術的障壁

### 壁の全体像

電子カルテに Amazon Bedrock や Azure OpenAI を連携させてAI機能を実装しようとすると、
複数の技術的・制度的障壁にぶつかる。

#### 障壁1：データの形式が標準化されていない

電子カルテに蓄積されている患者データは：
- ベンダー固有の独自形式で保存されている
- AIツールに「患者データを渡す」APIが存在しない（または公開されていない）
- 必要なデータを抽出するだけでも、ベンダーとの個別交渉・開発が必要

AIに学習させるためのデータ整備コストが非常に高くなる。
これはHL7 FHIRが普及することで改善されるが、現状では未整備。

#### 障壁2：クラウド接続に対するセキュリティ規制

厚生労働省の「医療情報システムの安全管理に関するガイドライン第6.0版」（2023年5月改訂）では、
患者データをクラウドに送る場合の責任分界を厳密に定めている。

医療機関が気にするポイント：
- **患者データの院外流出リスク**：プロンプトに患者情報を含む場合、
  その情報がAIベンダー（OpenAI, Anthropic等）のサーバーに送信・保存されるリスク
- **責任の所在**：データ漏洩が起きた場合、病院が直接責任を負う
- **HIPAA等海外規制との抵触**（グローバルなAIサービスを使う場合）

この恐れから、多くの病院は「とにかくクラウドは怖い」という判断をしがちで、
外部のAIサービスとの連携を拒む傾向がある。

#### 障壁3：APIの不在または非公開

多くの既存電子カルテシステムは、外部システムとの連携を想定した設計になっていない。
- REST APIが存在しない、または内部でしか使えない閉鎖的な仕様
- APIが存在しても、仕様書が公開されておらず、ベンダーとNDA（秘密保持契約）を結ばないと利用できない
- HL7 FHIRに対応していないシステムでは、データの読み書き自体に特注開発が必要

#### 障壁4：AIが生成した内容の医療責任問題

AIが生成した診断支援情報や文書ドラフトについて：
- 「AIが誤った判断をして患者に害が及んだ場合、誰が責任を取るのか？」という問いに
  法的に明確な答えがまだない
- このため、電子カルテへのAI出力の**直接書き込みは法的グレーゾーン**とされ、
  多くの病院が「あくまで参考情報として表示するだけ」にとどめている

#### 障壁5：ベンダーの利益相反

電子カルテベンダー自身もAI機能を開発・販売したい。
そのため、他社のAIサービスとの接続仕様を積極的に公開しない動機がある。
「うちの電子カルテを使うなら、AIもうちのAIソリューションを使ってください」
という商業的な閉鎖性が生まれやすい構造。

### 現実的な回避策として採られているアプローチ

**オンプレミスAI（院内完結型）**：
- Amazon Bedrock や Azure OpenAI を使わず、病院の院内サーバーに
  オープンソースのLLM（大規模言語モデル）を設置する
- 那須赤十字病院の事例（2024年）：リコーのGPUサーバー＋700億パラメータLLM＋「Dify」を
  オンプレミス環境に構築し、退院サマリー自動作成に活用
  - 電子カルテから情報を読み込み、看護記録・リハビリ記録をもとにドラフトを自動生成
  - 患者データが院外に出ないため、セキュリティリスクが極めて低い

**HL7 FHIRを介したAPI連携**：
- 日本IBM（2025年）は、61病院に導入するCIS（臨床情報システム）から
  HL7 FHIRを介してデータを取得し、退院サマリーのドラフトを自動生成するソリューションを開発
- Azure OpenAI、Amazon Bedrock、IBM watsonxの3基盤に対応可能
- 「電子カルテからFHIR経由でデータ取得→AIで処理→CISクライアントに戻す」という
  クリーンな連携モデルが実現しつつある

**Azure連携による患者統計の可視化**：
- HITO病院（四国中央病院グループ）の2024年事例
- 電子カルテネットワークとMicrosoft Azureを連携し、看護必要度のデータをリアルタイム分析
- 症状詳記（高額診療報酬の際に必要な文書）の自動生成にAzure OpenAI Serviceを活用
- 多言語対応、業務負担の可視化（Microsoft FabricとPower BIを活用）など多用途展開

## 4. 医療機器プログラム（SaMD）としての規制

### SaMDとは何か

SaMD（Software as a Medical Device：プログラム医療機器）とは、
単独のソフトウェアとして医療目的を果たすプログラムのことである。
ハードウェア医療機器に組み込まれておらず、スマートフォンやクラウドで動作するものも含む。

日本では2013年の薬機法（医薬品医療機器等法）改正により、
単体プログラムが医療機器の規制対象となった。

### クラス分類と規制の厳しさ

医療機器はリスクに応じて4つのクラスに分類される：

| クラス | リスクレベル | 例 |
|--------|------------|-----|
| クラスI | 最低リスク | 体重計アプリなど |
| クラスII | 中程度リスク | 診断支援AI（一般的なもの） |
| クラスIII | 高リスク | 重篤疾患の診断支援AI |
| クラスIV | 最高リスク | 生命維持装置の制御ソフトなど |

ほとんどのAI診断支援ソフトはクラスII〜IIIに分類され、
クラスIIは「認証」、クラスIII以上は「承認」が必要。

### 承認プロセスの概要

PMDA（独立行政法人 医薬品医療機器総合機構）が審査を担う。

主な要求事項：
1. **有効性の証明**：臨床試験データや既存研究による性能検証
2. **安全性の証明**：誤診断が生じた場合の影響評価
3. **品質管理システム**：QMS（Quality Management System）の整備
4. **不具合・副作用報告体制**：市販後の継続的な安全監視

AIに特有の追加要件：
- 機械学習モデルのバイアス評価
- 学習データの品質管理
- 市販後に性能が変化する可能性の評価

### 承認の現状（2025年時点）

- AI活用の診断支援ツールは**約50件が薬事承認済み**（2025年時点）
- 主な承認事例：
  - **EndoBRAIN（サイバネットシステム）**：2018年、大腸内視鏡でのポリープ腫瘍判定
    → 日本初の内視鏡AI医療機器
  - **富士フイルム**：2022年9月、上部消化管内視鏡での胃腫瘍・食道癌検出支援
  - **コニカミノルタ**：2021年10月、胸部X線画像での結節影・浸潤影検出支援

### 規制がAI統合を困難にする理由

#### 問題1：市販後のモデル更新ができない

AIは学習データを増やすほど性能が向上するが、承認取得後に：
- 学習データを追加すると「変更申請」が必要
- 変更申請には再度の審査が必要（数ヶ月〜1年以上かかる場合も）

これでは「継続的に学習・改善するAI」の本来の強みを活かせない。

#### 問題2：承認には膨大なコストがかかる

臨床試験の実施、PMDA相談費用、申請書類作成費用など、
クラスIII SaMDの承認取得には数千万円〜数億円のコストがかかるとされる。
スタートアップや中小企業が医療AIを開発しても、承認取得の壁で市場参入できない。

### 規制の改善策：IDATEN制度と審査迅速化

政府もこれらの問題を認識しており、改善策を講じている。

**IDATEN制度（変更計画確認制度）**：
- 2019年薬機法改正で導入
- 承認申請の段階であらかじめ「将来の変更計画」を提出・確認しておくことで、
  計画内の変更は都度の変更承認申請なしに届出だけで変更可能にする仕組み
- AI医療機器の「市販後の追加学習」に適用することで、性能改善のサイクルを速める

**審査体制の強化（2024年）**：
- 2024年7月1日、PMDAが「プログラム医療機器審査室」を**「プログラム医療機器審査部」に昇格**
- 審査員増員、2チーム体制に拡充
- AI特有の課題（機械学習のバイアス、市販後学習の評価）を専門に扱う部会を設置

**クラスIIの迅速化方針**：
- 一定要件を満たすクラスIIのSaMDについて審査期間を短縮する方針が示されている
- 目標として「AI診断ソフトを1年で早期承認」という方向性が打ち出されている

## 5. 病院IT調達の意思決定プロセス

### 複雑な合議制と長い意思決定サイクル

病院のIT調達は、企業のシステム導入とは異なる特殊な意思決定構造を持つ。

主要な関係者：

| 役職 | 役割・関心事 |
|------|------------|
| **院長** | 最終決裁権者。医師としての視点から「臨床現場への影響」を重視 |
| **副院長（医療情報担当）** | 医師免許を持ちながら情報システム管理を担う場合が多い |
| **事務長** | 病院経営の観点からコストと業務効率化を重視 |
| **情報システム室（IT担当）** | 技術的な評価を担う。ただし専任IT人員が少ない病院が多い |
| **看護部長** | 看護師の業務フローへの影響を代表する |
| **薬局長・検査部長** | 部門システムとの連携について意見を持つ |

### 意思決定の特徴

1. **委員会・ワーキンググループによる合議制**
   - 全体委員会と、業務・部署単位の分科会・WGが組織される
   - 多数の関係者のコンセンサスが必要なため、意思決定に1〜2年かかることも珍しくない

2. **「医師が使いやすいかどうか」が最重要**
   - 最終的な決裁者は院長（医師）であることが多い
   - 「臨床現場で医師が使いやすいかどうか」が最優先事項になる傾向
   - ITの観点（API連携性、将来のAI対応）は後回しになりやすい

3. **既存ベンダーへの依存が強化される構造**
   - 現行システムのベンダーはすでに「院内の業務フローを知っている」アドバンテージがある
   - デモ・提案段階でも、現行ベンダーは有利な条件で提示できる
   - 結果として「更新してもまた同じベンダー」になりがち

4. **専任IT人員の不足**
   - 日本の多くの中小病院には、専任の情報システム人員がいない、または1〜2名しかいない
   - ベンダーに依存せざるを得ない状況が、ベンダーの交渉力を高める

5. **調達支援サービスの存在**
   - 医療情報研究所（MEDIS）などが「医療CIO支援サービス・医療情報システム導入／更新支援業務」
     を提供し、医療機関の調達を支援している

### 電子カルテ選定の典型的なプロセス

1. **現状分析と課題整理**（3〜6ヶ月）
2. **要件定義・仕様書作成**（3〜6ヶ月）
3. **市場調査・RFP（提案依頼書）発行**
4. **各ベンダーへのデモ・ヒアリング**
5. **全体委員会での評価・選定**
6. **契約・導入準備**（6〜12ヶ月）
7. **稼働・定着化**（6ヶ月〜）

合計3〜5年かかるプロジェクトとなることも多い。
このサイクルの長さが、「新しいAI技術への対応が遅れる」理由のひとつでもある。

## 6. HISと外部クラウドサービス連携の事例

### 連携の類型

**タイプA：部分的クラウド活用（分析・可視化のみ）**
- 電子カルテ本体はオンプレミスのまま
- 匿名化・集計されたデータのみをクラウドに送り、分析や可視化に使う
- 個人を特定できる患者データはクラウドに送らない
- HITO病院の事例（Microsoft Azure + Power BI）がこれに近い

**タイプB：オンプレミスLLM（院内完結型）**
- クラウドを使わず、AIサーバーを病院内に設置
- 電子カルテから情報を直接読み込んで処理
- 那須赤十字病院の事例（リコー製LLM）がこれに該当
- データが院外に出ないため、セキュリティリスクが低い
- しかし、サーバー購入・維持コスト、専任技術者が必要

**タイプC：FHIR APIによるクラウドAI連携（次世代型）**
- HL7 FHIR形式でデータをAPI経由でやり取りし、クラウドAIと連携
- 日本IBMのソリューション（Azure OpenAI / Amazon Bedrock / IBM watsonx対応）がこれに近い
- HL7 FHIR対応済みの電子カルテが前提条件

### 具体的な連携事例

#### Wemex（ウィーメックス）× Microsoft Azure

旧PHC（パナソニックヘルスケア）系のWemexは、クリニック向け電子カルテ
「Medicom」のクラウド版をAzure上で構築。
- 厚労省の「2030年までに全国クリニックへのEMR普及」目標に合わせたクラウド化
- .NET/C#開発エンジニアに適したAzureを選択

#### 日本IBM × FHIR連携 AIソリューション（2025年）

- 全国61の病院施設でCIS（Clinical Information System）を稼働
- HL7 FHIRを介してカルテ情報を取得し、退院サマリーのドラフトを自動生成
- Azure OpenAI、Amazon Bedrock、IBM watsonxの3つのAI基盤に対応
- 各病院の要件・予算・セキュリティポリシーに合わせてAI基盤を選べる柔軟な設計

#### HITO病院 × Azure OpenAI Service（2024年）

- 愛媛県の四国中央病院グループの病院
- 電子カルテとAzureネットワークを接続し、以下を実現：
  - 症状詳記の自動生成（高額診療報酬申請に必要な文書）
  - 看護必要度・業務負担のリアルタイム可視化（Power BI）
  - 多言語対応（海外人材の夜勤対応に活用）
  - 患者への個別化した食事指導・リハビリメニューの生成
- 電子カルテのデータを**直接Azure OpenAIに送るのではなく**、
  必要な集計値や文書ドラフト生成に限定してリスクを管理

#### 那須赤十字病院 × リコー製LLM オンプレミス（2024〜2025年）

- 栃木県の中規模病院
- リコーが提供するGPUサーバー＋700億パラメータLLM＋Difyを院内設置
- 電子カルテから看護記録・リハビリ記録を読み込み、退院サマリーのドラフトを生成
- 特徴：
  - 患者データが院外に出ない（クラウド不使用）
  - オープンソース活用でコスト低減
  - 2024年7月プロジェクト開始、一部医師でのトライアルを経て全院展開を目指す
